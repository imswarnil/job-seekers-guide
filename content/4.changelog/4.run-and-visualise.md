## /run

There is now a [playground](/run). Type SQL, press Run, and see what the engine
did with it:

- **The row funnel.** `FROM applicants: 8` → `WHERE offers > 0: 5` → `GROUP BY
  branch: 3`. Those numbers are obtained by executing your query with its later
  clauses removed and counting what comes back. Change the `WHERE` and they
  move, because they were never a picture of anything else.
- **The query plan.** SQLite's own `EXPLAIN QUERY PLAN`, verbatim. `SCAN` means
  it read every row; `SEARCH` means it used an index. That one difference is the
  answer to half of "why is this slow".
- **For Java**, the compile and run stages separately. When `javac` fails, the
  JVM stage is drawn as never started — because it was. A compile error and a
  runtime crash are different failures with different fixes, and telling them
  apart is most of the first hundred hours.

Every figure carries where it came from. Anything read out of your source rather
than measured at runtime is marked as such, and anything that could not be
measured honestly is left blank with the reason instead of being estimated.

A run is a link: the Share button puts your code in the URL.
