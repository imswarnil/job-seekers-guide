## Why this matters in a job

Because "why not just use a file?" is a real question with a real answer, and
being able to give it is the difference between using a database and being
afraid of one.

## The admissions example, in a file

1,420 applicants, 120 seats, four programmes. Put it in a CSV:

```text [applications.csv]
id,name,email,programme,campus_city,fee_paid
1,Anita Rao,anita@example.com,B.Tech CSE,Pune,1200
2,Rahul Menon,rahul@example.com,B.Tech CSE,Pune,1200
3,Anita Rao,anita@example.com,B.Sc Physics,Pune,900
```

It works. Then, in order, these things happen:

::steps{level="3"}

### Two people open it at once

Both save. One person's changes are gone, silently, with no record that they
ever existed.

### The city gets renamed

`Pune` appears in 1,420 rows. You fix 1,418 of them.

### Someone types the fee as `12OO`

Nothing stops them. The total is now wrong and nobody knows which row did it.

### You need "applicants per programme, sorted by fee"

You write a script. Then another script. Then a script that reads the first
script's output.

### The file reaches 4 GB

Finding one row means reading all of them.

::

## What a database adds

| Problem above | What a database gives you |
| --- | --- |
| Lost update | **Transactions** — concurrent changes that do not silently destroy each other |
| Renaming in 1,420 places | **Normalisation** — store the city once, refer to it everywhere |
| `12OO` as a fee | **Types and constraints** — the column refuses non-numbers |
| Scripts on scripts | **A query language** — say what you want, not how to get it |
| Reading 4 GB to find a row | **Indexes** — find it without reading everything |

## The relational model in one paragraph

Data lives in **tables** (rows and columns). Each row is identified by a
**primary key**. A row can refer to a row in another table by storing its key —
a **foreign key**. That is the whole model, and it has survived fifty years of
attempts to replace it because those two ideas compose endlessly.

```sql
CREATE TABLE programme (
    id    INT PRIMARY KEY,
    name  TEXT NOT NULL,
    seats INT  NOT NULL CHECK (seats > 0)
);

CREATE TABLE applicant (
    id           INT PRIMARY KEY,
    name         TEXT NOT NULL,
    email        TEXT NOT NULL UNIQUE,
    programme_id INT  NOT NULL REFERENCES programme(id)
);
```

Read those two statements again. Every problem in the numbered list above is
prevented by something visible in them.

::tip{icon="i-lucide-shield-check"}
Constraints are not bureaucracy. Every constraint you decline to write becomes a
bug you find in production, at which point the bad data is already there and
somebody has to clean it up by hand.
::

## When a file *is* enough

Configuration, logs, a one-off export, and anything read by exactly one program
that never changes it concurrently. Reaching for a database there is its own
mistake. The question is never "database or file" in the abstract — it is
"who writes this, how often, and what breaks if two of them do it at once".

## The interview question this answers

**"Why use a database instead of files?"**

Concurrency, integrity and querying. A database lets many clients read and write
safely at once, enforces types and relationships so bad data cannot get in, and
answers questions without you writing the search by hand — and it does the last
one quickly because of indexes.
