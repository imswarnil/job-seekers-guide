## Why this matters in a job

Because half of debugging is knowing which stage broke. A compile error, a
runtime crash, and a wrong answer are three different failures with three
different fixes, and a developer who cannot tell them apart will paste all three
into the same search box and get lucky at a third of the rate of everyone else.

## Text to electricity, in five stages

::steps{level="3"}

### You write text

`Admissions.java` is a text file. Nothing about it is special — you could open
it in Notepad. It follows rules strict enough that a program can read it without
guessing.

### A compiler translates it

The compiler reads your text and produces instructions the machine can execute.
If your text breaks the rules, it refuses and tells you where. **That is a
compile error, and it happens before anything runs.**

```bash
javac Admissions.java     # produces Admissions.class
```

### The operating system loads it

You ask the OS to run it. The OS allocates memory, copies the instructions in,
sets up a stack for the program's function calls and a heap for the data it
creates, and hands the CPU a starting address. The running thing now has a name:
a **process**.

```bash
java Admissions
```

### The CPU executes, one instruction at a time

Fetch, decode, execute, repeat — billions of times a second. When your program
asks for something it is not allowed to do directly, like reading a file or
sending a network packet, it asks the OS to do it. That request is a **system
call**, and it is the boundary between your code and the machine.

### It ends, or it does not

The process exits and the OS reclaims its memory. If it crashed instead, that is
a **runtime error** — the code was valid, the situation was not. If it finished
happily and printed the wrong number, that is a **logic error**, and nothing but
you will catch it.

::

## Compiled, interpreted, and the honest middle

::tabs
  :::tabs-item{label="Compiled" icon="i-lucide-cpu"}
  C and C++ translate all the way down to machine instructions before running.
  Fastest, least forgiving, and the errors arrive before you ship.
  :::

  :::tabs-item{label="Interpreted" icon="i-lucide-play"}
  Python reads and executes your source as it goes. Fastest to write, slowest to
  run, and mistakes surface only when that line is finally reached.
  :::

  :::tabs-item{label="Both" icon="i-lucide-layers"}
  Java compiles to bytecode, and a virtual machine executes the bytecode —
  translating the hot parts to machine code while it runs. This is why Java both
  compiles and needs a runtime installed, which confuses everybody once.
  :::
::

## The three failures, named

| Failure | When | Who tells you | Example |
| --- | --- | --- | --- |
| Compile error | Before running | The compiler | Missing semicolon; wrong type |
| Runtime error | While running | The runtime, loudly | Divide by zero; file not found |
| Logic error | Never | Nobody. Or a user. | Applicants per seat computed upside down |

::warning{icon="i-lucide-alert-triangle"}
Logic errors are the expensive ones, and they are the entire reason testing and
code review exist as industry practices. You will meet both in Software
Engineering.
::

## What to skip, for now

You do not need to know what a linker does, what a register is, or how a JIT
compiler decides what to optimise. Those are real and interesting and they are
not on the path to your first job. Come back to them when you are curious, not
because a roadmap told you to.

## The interview question this answers

**"What is the difference between compiled and interpreted languages?"**

A compiled language is translated to machine instructions ahead of time by a
compiler, so errors in structure appear before it runs and execution is fast. An
interpreted language is translated as it executes, which is more flexible and
slower. Java sits in between: it compiles to bytecode, and the JVM executes that.
