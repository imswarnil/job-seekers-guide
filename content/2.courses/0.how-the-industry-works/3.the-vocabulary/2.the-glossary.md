## Why this matters in a job

Because nobody will define these for you. They will be used in a sentence, in a
meeting, at speed, and asking what one means feels expensive at the exact moment
you are trying to look competent. Read this once now and that moment does not
arrive.

## Building

::field-group
  ::field{name="Repository (repo)" type="git"}
  The project folder, with its whole history. "It's in the repo" means "it is in
  the project, go read it".
  ::

  ::field{name="Branch" type="git"}
  A separate line of work off the main code, so unfinished changes do not affect
  everybody else.
  ::

  ::field{name="Pull request (PR) / Merge request" type="git"}
  A proposal to merge your branch, with room for review comments. The unit of
  work most teams actually think in.
  ::

  ::field{name="Code review" type="practice"}
  A teammate reads your PR before it merges. Catches bugs, spreads knowledge, and
  is not a personal evaluation.
  ::

  ::field{name="Refactor" type="practice"}
  Changing how code is written without changing what it does. Distinct from a
  fix and from a feature, and worth saying precisely.
  ::

  ::field{name="Technical debt" type="practice"}
  Shortcuts taken deliberately or otherwise, which cost interest later in slower
  changes. Real, and often a reasonable trade.
  ::
::

## Running

::field-group
  ::field{name="Environment" type="ops"}
  A place the software runs. **Local** is your machine, **dev** and **staging**
  are rehearsals, **production** ("prod") is where real users are.
  ::

  ::field{name="Deploy / release" type="ops"}
  Putting a version into an environment. "We deployed to prod" means users have
  it now.
  ::

  ::field{name="Rollback" type="ops"}
  Putting the previous version back, quickly, because the new one misbehaved.
  ::

  ::field{name="CI/CD" type="ops"}
  Continuous integration and delivery: the automation that tests every PR and
  deploys every merge, so nobody does it by hand.
  ::

  ::field{name="On-call" type="ops"}
  Being the person an alert wakes up. Rotated, usually compensated, and normal
  at product companies.
  ::

  ::field{name="Incident / postmortem" type="ops"}
  Something broke in production; afterwards, a blameless written account of why
  and what changes.
  ::

  ::field{name="SLA / uptime" type="ops"}
  The promise about how available the service will be, and the measurement of
  whether it was kept.
  ::
::

## Deciding

::field-group
  ::field{name="MVP" type="product"}
  Minimum viable product — the smallest version that delivers real value and
  tells you whether you were right.
  ::

  ::field{name="Scope" type="product"}
  What is in and what is out. **Scope creep** is the boundary quietly moving.
  ::

  ::field{name="Roadmap" type="product"}
  What is planned, roughly in order. A plan, not a promise.
  ::

  ::field{name="Requirement / acceptance criteria" type="product"}
  What must be true for the ticket to be done. Ask for it when it is missing.
  ::

  ::field{name="Stakeholder" type="product"}
  Anybody affected by the decision who is not building it.
  ::
::

## The ritual language

**Agile** is the umbrella idea: build in small increments, get feedback, adjust.
**Scrum** is the most common concrete implementation of it, with sprints,
standups, grooming, demos and retros. **Kanban** is the other common one: a
continuous board with limits on how much can be in progress at once, and no
sprints. Teams say "agile" and mean "scrum" roughly always.

::warning{icon="i-lucide-alert-triangle"}
Do not memorise these as definitions to recite. Interviewers can tell instantly.
Learn them well enough to use in a sentence about something you have actually
done, however small.
::

## What you can safely ignore

Every three-letter acronym that appears only in a job description's "nice to
have" list. If it is genuinely required, it will appear in the interview, and by
then you will know how to learn one quickly — which is the actual skill.

## The interview question this answers

**"What is CI/CD, and why does it matter?"**

Automation that tests every change and deploys every approved one. It matters
because it makes releasing boring, and boring releases mean the team can ship
small changes often instead of large risky ones rarely.
