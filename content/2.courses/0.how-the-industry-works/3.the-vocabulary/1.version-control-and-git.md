## Why this matters in a job

Because there is no job without it. Not one. Git is the only tool in this entire
module that you will touch on literally every working day, and it is the thing
self-taught developers most often arrive without.

## What it is

**Version control records every change to a set of files, who made it, when, and
why — and lets many people change the same files without destroying each other's
work.**

Before it, teams emailed `report_final_v2_FINAL_use_this.doc` around. That is not
a joke about documents; that is how software was built, and it went exactly as
badly as you would expect.

## The model, in one paragraph

Your project is a folder. Git stores **snapshots** of that folder called
**commits**, each one pointing at the one before it, forming a history. A
**branch** is a movable label pointing at a commit, so you can build a chain of
commits off to the side without disturbing the main line. **Merging** joins two
chains back together. A **remote** is a copy of the whole history living on a
server — GitHub, GitLab — so the team shares one history.

## The six commands

```bash
git clone <url>          # 1. get a copy of the project
git checkout -b my-fix   # 2. start a branch for your change
git add .                # 3. stage the changes you want to keep
git commit -m "message"  # 4. record them as a snapshot
git push -u origin my-fix # 5. send the branch to the server
git pull origin main     # 6. bring other people's work into yours
```

That is 95% of daily use. Everything else you will look up the three times a
year you need it, exactly like everybody else on your team does.

## The one that will bite you

A **merge conflict** happens when two people changed the same lines and Git will
not guess which one wins. It looks like this in the file:

```text
<<<<<<< HEAD
int seats = 120;
=======
int seats = 140;
>>>>>>> feature/increase-intake
```

Delete the markers, leave the code you want, commit. It feels like an emergency
the first time and like a Tuesday by the tenth.

::tip{icon="i-lucide-message-circle"}
Write commit messages as instructions to the codebase, in the present tense:
*"Count seats per programme"*, not *"changed seat counting"* and definitely not
*"fix"*. Six months later you will be the person reading them.
::

## Do this now, before the next lesson

::steps{level="3"}

### Make a GitHub account

Use a professional username. It goes on your resume.

### Create a repository

Public. Call it anything.

### Clone it, add a file, commit, push

Then refresh the page on GitHub and see your file there.

### Do it again from a branch, and open a pull request against yourself

This takes ten minutes and puts you ahead of a surprising number of candidates.

::

## What to skip, for now

Rebasing, cherry-picking, submodules, reflog, bisect. All real, all useful
eventually, none of them needed to work productively on a team this year.

## The interview question this answers

**"How do you use Git in a team?"**

Branch off main for each change, commit in small logical pieces, push, open a
pull request, get it reviewed, merge. Pull from main often so conflicts stay
small. That answer describes an actual professional workflow, which is what the
question is checking for.
