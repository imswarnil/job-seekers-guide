The day it fails you lose everything, unless there is a copy somewhere else. Git
calls that copy a **remote**, and the usual place to keep one is GitHub.

## Why this matters in a job

Two reasons, and the second one is bigger than people realise.

The obvious one: a project that exists only on your laptop is one accident away
from not existing. The other: your GitHub profile is the only portfolio a hiring
manager can check without taking your word for anything. It shows what you build,
how you commit, and — the part nobody thinks about — whether you keep going.

::real-life{title="What a recruiter actually looks at" source="A hiring manager, thirty seconds per profile"}
Not the star counts. Three things: is there a project with more than ten commits,
do the commit messages read like a person wrote them, and is there a README that
explains what the thing is. A profile with one real project and a good README
beats a profile with fourteen forked tutorials, every time, and it is not close.
::

## Set up your account and your key

Create a GitHub account if you have not. Then connect the key you generated two
lessons ago — you already did the hard part.

```bash [Terminal]
cat ~/.ssh/id_ed25519.pub
```

```text [Output]
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIH8pW9K…8sQ swarnil@example.com
```

Copy that whole line. On GitHub: **Settings → SSH and GPG keys → New SSH key**,
paste, save.

::caution{icon="i-lucide-shield-alert"}
That is the `.pub` file — the public half. The file without `.pub` never leaves
your machine and never goes into a web form. If you have pasted the wrong one
anywhere, generate a new pair and remove the old key from every service it was
added to.
::

Test it:

```bash [Terminal]
ssh -T git@github.com
```

```text [Output]
Hi swarnil! You've successfully authenticated, but GitHub does not provide shell access.
```

That is a success. The server knows who you are and is declining to give you a
prompt, which is exactly right.

## Connect your repository

Make an empty repository on GitHub — call it `university-management-app` — and
**do not** let it add a README, a licence or a `.gitignore`. You already have a
history and you want an empty container to put it in.

```bash [Terminal]
cd ~/projects/university-management-app
git remote add origin git@github.com:yourname/university-management-app.git
git remote -v
```

```text [Output]
origin	git@github.com:yourname/university-management-app.git (fetch)
origin	git@github.com:yourname/university-management-app.git (push)
```

`origin` is just a nickname for that URL. It is a convention, not a keyword — you
could call it anything, and everybody calls it origin.

```bash [Terminal]
git push -u origin main
```

```text [Output]
Enumerating objects: 12, done.
Writing objects: 100% (12/12), 1.42 KiB | 1.42 MiB/s, done.
To github.com:yourname/university-management-app.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

Refresh the page. Your four commits are there, with their messages, and every
file you committed. That is the second copy.

`-u` sets the connection between your local `main` and the remote's `main`, so
from now on plain `git push` and `git pull` know where to go. You need it once.

## The loop, from here on

::flow{numbered caption="Every working day, for the rest of your career."}
  :::flow-step{label="git pull" icon="i-lucide-download"}
  Bring down anything that changed elsewhere — another machine, a teammate.
  Before you start, always.
  :::
  :::flow-step{label="Work, and commit" icon="i-lucide-file-pen"}
  Small commits, honest messages. Several a day.
  :::
  :::flow-step{label="git push" icon="i-lucide-upload" highlight}
  Send your commits up. Now they exist in two places and one of them is not your
  laptop.
  :::
::

## The three you will use for other people's code

```bash [Terminal]
git clone git@github.com:someone/their-project.git
```

Downloads a repository and its entire history, and sets `origin` up for you. This
is the "clone the repo and run it" from your first day at a job, and it is one
command.

```bash [Terminal]
git pull
```

Fetches new commits from the remote and merges them into your branch. Run it
before you start work, not after.

```bash [Terminal]
git push
```

Sends your commits up. If it is rejected, that is not a failure — it means the
remote has commits you do not, and Git is refusing to overwrite them:

```text [Output]
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:yourname/university-management-app.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref.
```

The fix is `git pull`, resolve anything that conflicts, then push. **The fix is
never `--force`.** That command exists, it overwrites the remote history with
yours, and on a shared repository it deletes somebody else's work. It gets its
own section in two lessons' time and this is your early warning.

## Making the profile worth looking at

Two things, both cheap, both disproportionately effective.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-book-open" title="A README that explains it"}
  What the project is, what it does, how to run it, and what you learned. Written
  for a stranger with thirty seconds. This is the single highest-return file in
  any repository.
  :::
  :::feature{icon="i-lucide-calendar-days" title="Commits over months"}
  Fifty commits across four months says something twenty commits in one weekend
  does not. Nothing you can fake, which is exactly why it is read.
  :::
::

Write the README as you go rather than at the end. The University Management App
will grow for a year, and a README written in month one and updated as you build
is a genuinely useful document by the time somebody asks for it.

::tip{icon="i-lucide-lightbulb"}
Make the repository public from the start. There is nothing in it worth hiding,
and a private repository does nothing for you in a job search. If you are
embarrassed by the early commits — everybody is — remember that the visible
improvement over time is the strongest thing on the profile.
::

## What confuses people here

**Local and remote are two separate copies of the history.** Committing changes
your machine only. Nothing appears on GitHub until you push, and nothing arrives
from GitHub until you pull. People lose a week of work sitting in unpushed
commits on a dead laptop, having believed that committing was enough.

**`origin` is not a special word.** It is the default nickname for the remote you
cloned from, and nothing more.

## What you can do now

You have your work in two places, connected with a key rather than a password,
and the beginning of a profile that will be looked at. You can also clone
anybody's project and run it, which is the first thing you will be asked to do at
work.

    icon: i-lucide-circle-help
    content: Somebody — possibly you, from another machine, possibly the GitHub web editor — added commits to the remote that your copy does not have. Git refuses rather than throw them away. The fix is `git pull` to bring them down and merge, resolve anything that conflicts, then push. Forcing would replace the remote history with yours and delete their commits, which is why the hint text does not mention it.
  - label: "Interviewers ask this — what is the difference between `git fetch` and `git pull`?"
    icon: i-lucide-briefcase
    content: "`git fetch` downloads the new commits from the remote but leaves your working branch untouched, so you can look at what has arrived before deciding. `git pull` is fetch plus merge — it brings them down and immediately integrates them into your current branch. On a shared project, careful people fetch and inspect before merging; most of the time on your own work, pull is fine. Knowing that pull is two operations is the answer they are after."
