Every professional on earth solved this the same way: a tool that records every
version of every file, forever, and lets you go back to any of them. It is called
version control, and the one everybody uses is Git.

## Why this matters in a job

Because it is not optional anywhere. Every team, every project, every code test.
"Send me your GitHub" is a normal sentence in a first phone call, and a candidate
whose answer is a zip file has told the interviewer something before the
technical round starts.

It is also the tool that makes you unafraid. Everything you have learned so far
has had a warning attached: `rm` has no undo, `>` overwrites silently. Git is
the answer to all of it.

## The folder you already have

You have done this, in some form. So had I.

```text
university-project/
  report.docx
  report-v2.docx
  report-v2-final.docx
  report-v2-final-ACTUAL.docx
  report-v2-final-ACTUAL-priya-comments.docx
  report-old-DO-NOT-DELETE.docx
```

::pros-cons
---
title: Copying the folder as your backup strategy
pros:
  - It works, for about a week
  - It requires learning nothing
  - You can see the versions with your own eyes
cons:
  - Nothing records what changed between two of them, or why
  - Nothing records when, or who
  - Two people cannot work at once without one of them losing work
  - Going back means guessing which copy was good
  - The folder is 4 GB and 90% of it is duplicates
---
::

The problem is not tidiness. It is that **a copy stores a state and throws away
the change.** You can see that there are two versions and you cannot see what
happened between them, which is exactly the thing you need to know.

## What Git stores instead

A **commit** is a snapshot of your whole project at one moment, plus who made it,
when, and a message saying why. Commits are linked, each one pointing at the one
before, so together they form a history you can walk.

::flow{numbered direction="vertical" caption="A history of the University Management App, three days in. Each commit knows its parent."}
  :::flow-step{label="Set up the project folders" icon="i-lucide-folder-plus"}
  Monday, 09:12. Four folders and an empty README.
  :::
  :::flow-step{label="Add the applicant data" icon="i-lucide-file-plus"}
  Monday, 14:40. `applicants.csv`, twelve rows.
  :::
  :::flow-step{label="Add the shortlist report" icon="i-lucide-terminal" highlight}
  Tuesday, 10:05. `reports/shortlist-by-source.sh`. You are here.
  :::
::

Four things fall out of that, and each one is a thing the copied folder cannot
do:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-history" title="Go back to any point"}
  Not "roughly around when it worked". Exactly the state of every file at 14:40
  on Monday.
  :::
  :::feature{icon="i-lucide-git-compare" title="See what changed"}
  Line by line, between any two moments, in any file.
  :::
  :::feature{icon="i-lucide-user-check" title="Know who and why"}
  Every line of code in a professional project can be traced to a person, a date
  and a message. This is used daily, and not for blame.
  :::
  :::feature{icon="i-lucide-users" title="Work in parallel"}
  Several people changing the same project at once, with a defined way of
  combining the results.
  :::
::

::real-life{title="git blame, and why it is not about blame" source="Any team, any week"}
A number in a config file is wrong and nobody knows why it is 30. One command
shows the line was changed fourteen months ago by somebody who left, with the
message "raise pool size, see incident 2024-11-03". Now the change is
understandable, the incident is findable, and it can be adjusted with confidence
rather than reverted in the dark. That is the real value: a project's history is
its reasoning, and the tool that stores it is the only reason the reasoning
survives the people.
::

## Not a backup, and not a cloud drive

Two comparisons worth being precise about, because interviewers ask and beginners
conflate them.

::compare{caption="A synced folder and a version control system look similar and are not."}
  :::compare-side{label="A cloud drive" verdict="neutral"}
  Syncs the current state automatically. Keeps some recent versions. Has no idea
  what a change *means*, cannot combine two people's edits to the same file
  sensibly, and never asks you to explain yourself.
  :::
  :::compare-side{label="Git" verdict="right"}
  Records deliberate snapshots with messages. Shows exactly what changed between
  any two. Merges parallel work with rules, and stops and asks when the rules are
  not enough.
  :::
::

The key word is **deliberate**. Git does not record what you are doing; it
records what you decide is worth recording, which is why the history is readable
a year later.

## What confuses people here

::warning{icon="i-lucide-alert-triangle"}
**Git and GitHub are not the same thing.** Git is the tool, running on your
machine, working entirely offline. GitHub is a website that hosts copies of Git
repositories and adds things on top: reviews, issues, permissions. You can use
Git for ten years without GitHub. Getting this wrong in an interview is a small
thing that lands badly, because everybody notices it.
::

The second confusion is scale. Git is not for large projects and teams. It is for
a folder with three files in it, from the first day, because the value is not
collaboration. It is the ability to change something boldly and get back.

## Your turn

No commands yet. Two minutes of thinking:

1. Find a real folder on your machine with more than one version of the same file
   in it. Look at the names.
2. For any two of them, can you say what actually changed? Try. This is the
   experience the rest of the chapter removes.
3. Write down, in one sentence, the last time you lost work or were afraid to
   change something because you might.

::accordion
---
items:
  - label: Why the third question is the one that matters
    icon: i-lucide-key

## Check yourself

::accordion
---
items:
  - label: What does a commit actually contain?
    icon: i-lucide-circle-help
    content: A snapshot of the tracked files at that moment, the author, the timestamp, a message explaining why, and a pointer to the commit before it. That last part is what makes the history a chain rather than a pile. You can walk backwards from any point and see how the project got there.
  - label: "Interviewers ask this: what is the difference between Git and GitHub?"
    icon: i-lucide-briefcase
    content: Git is the version control system itself, running locally, with the full history on your machine and no network needed. GitHub is a hosting service for Git repositories that adds collaboration on top (pull requests, reviews, issues, access control, automation). GitLab and Bitbucket do the same job. It is a warm-up question, and the reason it is asked is that a surprising number of people who list Git on a CV have only ever used a website.
---
::
