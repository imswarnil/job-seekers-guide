Four commands: `git init`, `git add`, `git commit`, `git log`. Between the second
and the third sits the one part of Git that confuses everybody at first, and it
is worth the three minutes it takes to understand rather than the three weeks of
copying commands.

## Why this matters in a job

Because this is the loop. Not the exotic commands. This. Change something, stage
it, commit it with a message that will mean something to a stranger. You will run
it several times a day for the rest of your working life, and how well you do it
is visible to everyone who reads your history.

## Tell Git who you are, once

Before the first commit on a new machine:

```bash [Terminal]
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
```

That name and email are stamped on every commit you ever make, and on a public
repository they are visible forever. Use the email you are happy to be contacted
on.

## Start a repository

```bash [Terminal]
cd ~/projects/university-management-app
git init
```

```text [Output]
Initialized empty Git repository in /Users/swarnil/projects/university-management-app/.git/
```

One command. That is the whole setup, and it works offline with no account
anywhere.

```bash [Terminal]
ls -la
```

```text [Output]
drwxr-xr-x  9 swarnil  staff  288 19 Aug 14:02 .
drwxr-xr-x  3 swarnil  staff   96 19 Aug 12:02 ..
drwxr-xr-x 12 swarnil  staff  384 19 Aug 14:02 .git
-rw-r--r--  1 swarnil  staff  842 19 Aug 13:40 applicants.csv
drwxr-xr-x  2 swarnil  staff   64 19 Aug 12:02 java-tools
drwxr-xr-x  2 swarnil  staff   64 19 Aug 12:02 notes
drwxr-xr-x  2 swarnil  staff   64 19 Aug 12:02 sql
drwxr-xr-x  2 swarnil  staff   64 19 Aug 12:02 web
```

There is `.git`, a hidden folder holding the entire history. Notice that you can
only see it because of `ls -la`, which is a lesson from two chapters ago paying
for itself.

::warning{icon="i-lucide-alert-triangle"}
Delete `.git` and you delete the whole history, permanently, with the project
files left innocently in place. It is the one folder never to tidy away.
::

## Where things stand

```bash [Terminal]
git status
```

```text [Output]
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	applicants.csv
	java-tools/
	notes/
	sql/
	web/

nothing added to commit but untracked files present
```

**Run `git status` constantly.** Before every command and after every command,
for the first month. It tells you where you are, what has changed and, every
single time, what to type next. It is the most helpful thing in the tool and
beginners underuse it badly.

## The three places a file can be

Here is the bit that confuses people. A file in a Git project is in one of three
states, and every command moves it between them.

::flow{numbered caption="The only diagram you need for the whole of Git's daily loop."}
  :::flow-step{label="Working directory" icon="i-lucide-file-pen"}
  The files as they are on disk right now. You edit here. Git knows they have
  changed and has recorded nothing.
  :::
  :::flow-step{label="Staging area" icon="i-lucide-inbox" highlight}
  A list of the changes you have chosen to include in the next commit. `git add`
  puts things here. Nothing is permanent yet.
  :::
  :::flow-step{label="History" icon="i-lucide-git-commit-horizontal"}
  The commits. Permanent, message attached. `git commit` moves everything staged
  into a new one.
  :::
::

Why the middle step exists, since everybody's first reaction is that it is a
pointless extra: **because a commit should be one idea, and an afternoon of work
is usually three.** You fixed a bug, renamed a folder and added a report. Staging
lets you commit those separately, with three honest messages, instead of one
commit called "changes" that nobody can ever unpick.

::real-life{title="What a bad history costs, eight months later" source="Reading somebody else's project"}
Two projects, same size. One has forty commits called "update", "fix", "changes"
and "work". The other has forty commits that each name one change. When something
breaks, the second project can be bisected: you find the exact commit that
introduced the bug in about four minutes. The first cannot be, and you read
everything. The difference took no extra time to create.
::

## Staging and committing

```bash [Terminal]
git add applicants.csv
git status
```

```text [Output]
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   applicants.csv

Untracked files:
	java-tools/
	notes/
	sql/
	web/
```

One file staged, the rest untracked. To stage everything:

```bash [Terminal]
git add .
```

The `.` means "this folder and everything below it". Convenient, and worth a
moment of suspicion: `git status` first, so you know what you are sweeping in.

```bash [Terminal]
git commit -m "Set up the University Management App project structure and applicant data"
```

```text [Output]
[main (root-commit) 3f7a1c9] Set up the University Management App project structure and applicant data
 2 files changed, 13 insertions(+)
 create mode 100644 applicants.csv
 create mode 100644 README.md
```

That `3f7a1c9` is the commit's identity: a hash, unique to that exact snapshot.
You will use short forms of these constantly.

::tip{icon="i-lucide-lightbulb"}
Empty folders are invisible to Git. It tracks files, not directories, so
`java-tools/`, `sql/` and `web/` did not get committed. There was nothing in
them. This surprises everybody once. The usual fix is a placeholder file, and
later they fill up on their own.
::

## Writing a message somebody will thank you for

The convention, and it is close to universal:

::compare{caption="The same commit, two messages."}
  :::compare-side{label="What beginners write" verdict="wrong"}
  `git commit -m "update"`

  In six months this tells you nothing. In a list of forty, it tells you less
  than nothing, because it makes the whole history unsearchable.
  :::
  :::compare-side{label="What the team wants" verdict="right"}
  `git commit -m "Add applicant CSV and shortlist-by-source report"`

  Present tense, one line, says what changed. Read as "this commit will…". Under
  about seventy characters.
  :::
::

## Reading the history

```bash [Terminal]
git log
```

```text [Output]
commit 3f7a1c9e2b8d4f1a6c0e9d7b5a3f2e1c8d6b4a20 (HEAD -> main)
Author: Swarnil Singhai <you@example.com>
Date:   Tue Aug 19 14:07:22 2026 +0530

    Set up the University Management App project structure and applicant data
```

Verbose. This is the version people actually use:

```bash [Terminal]
git log --oneline
```

```text [Output]
3f7a1c9 Set up the University Management App project structure and applicant data
```

And to see what actually changed:

```bash [Terminal]
git diff
```

Shows the changes you have made but not staged. `git diff --staged` shows what is
staged and about to be committed. Reading your own diff before committing is a
habit worth building now. It catches the debug line you forgot to delete, every
time.

## Keeping things out

Some files must never be committed: secrets, dependency folders, build output,
anything enormous or machine-specific.

```bash [Terminal]
cat > .gitignore <<'EOF'
.env
.DS_Store
node_modules/
*.class
EOF
git add .gitignore
git commit -m "Ignore secrets, build output and OS files"
```

::caution{icon="i-lucide-shield-alert"}
`.env` holds passwords and API keys, and this line goes in before you ever create
one. A committed secret is not fixed by deleting it in a later commit. The
history still contains it, and on a public repository it will be found by an
automated scanner within minutes. The only real fix is to treat the key as
compromised and rotate it.
::

## What confuses people here

**`git add` does not save anything.** It only marks what will be in the next
commit. Nothing is recorded until `git commit`, and the number of beginners who
stage carefully and then close the laptop is high.

**A file changed after being staged is in two states at once**: the staged
version and the newer working version. `git status` shows both, under two
headings, and this is a design feature rather than a bug.

## What you can do now

You can turn any folder into a repository, see exactly what has changed, choose
what goes into a commit, write a message that will be useful to a stranger, and
read the history back. That is the daily loop, complete.

In `~/projects/university-management-app`, with `git status` after every step:

1. Add a real README: a title, two lines saying what the University Management
   App is, and a list of the four folders.
2. Stage and commit it, on its own, with a message about the README.

## Check yourself

::accordion
---
items:
  - label: You ran `git add report.sh`, then edited `report.sh` again, then committed. Which version is in the commit?
    icon: i-lucide-circle-help
    content: The version as it was when you ran `git add`. Staging takes a snapshot at that moment; the later edit is still sitting in your working directory, unstaged, and `git status` will tell you so under a separate heading. Committing again after a second `git add` captures it. This trips up nearly everyone once, and it is the clearest demonstration that the staging area is a real place rather than a formality.
  - label: "Interviewers ask this: what is the staging area for?"
    icon: i-lucide-briefcase
    content: It lets you choose which of your current changes belong in the next commit, so that a commit can be one coherent idea rather than everything you happened to do that afternoon. That matters because a history of single-purpose commits can be read, reviewed, reverted and bisected, and a history of "changes" cannot. The follow-up is often "so how do you split up work you have already done?", and the honest answer is `git add -p`, which stages one chunk at a time.
