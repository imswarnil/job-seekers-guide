Nobody decides in the sense you are imagining. A piece of software called the
**scheduler** gives each program a few milliseconds of the processor, snatches it
away, and gives it to the next one — thousands of times a second, fast enough
that everything looks simultaneous.

That software is part of the operating system, and it is the last thing standing
between you and a keyboard.

## Why this matters in a job

Because the operating system is the thing that says no to you. Permission denied.
Address already in use. Too many open files. Killed. Every one of those is the
operating system refusing a request, and every one of them is an error you will
meet in your first fortnight of real work.

You cannot argue with a component you do not know exists.

## What it actually is

An operating system is a program that starts first and never stops. Everything
else runs inside the world it provides. Strip it to its jobs and there are four.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-square-stack" title="It runs programs"}
  Loads them into memory, gives each one a turn on the processor, and cleans up
  after them when they end or crash.
  :::
  :::feature{icon="i-lucide-folder" title="It invents files"}
  Storage is a numbered sequence of blocks. Files, folders and names are the
  operating system's fiction, maintained for your benefit.
  :::
  :::feature{icon="i-lucide-shield" title="It enforces permissions"}
  Who owns what, who may read it, who may change it. Including refusing you.
  :::
  :::feature{icon="i-lucide-plug" title="It talks to the hardware"}
  Your code never touches the disk, the network card or the screen. It asks. The
  operating system does it, or declines.
  :::
::

## A process is a program that is actually running

Two words that get used interchangeably and should not be.

::compare{caption="The same thing, before and after you double-click it."}
  :::compare-side{label="A program" verdict="neutral"}
  A file on disk. Instructions sitting there, doing nothing, taking up space.
  Inert. There is one copy of it.
  :::
  :::compare-side{label="A process" verdict="neutral"}
  That program, loaded into memory and given a turn on the processor. It has its
  own memory, its own open files, its own identity number. Open the same program
  three times and you have three processes.
  :::
::

Each process gets its own private memory, and the operating system makes sure of
it. One process cannot read another's memory — which is why a crashing browser
tab does not take your unsaved document with it, and why a bug in one program
cannot quietly rewrite another's data.

The illusion is very good. It is still an illusion — on a single core, exactly one
process is executing at any instant, and the rest are waiting their turn. A
machine with eight cores genuinely runs eight at once, and schedules the other
four hundred.

## Asking permission: the system call

Your program cannot write to a file. It genuinely cannot — the processor runs it
in a restricted mode where the instructions that touch hardware are unavailable.
What it can do is ask.

::flow{numbered caption="What actually happens when a program saves an applicant's record."}
  :::flow-step{label="Your code says 'write this'" icon="i-lucide-file-pen"}
  A line in your program that looks like an ordinary function call.
  :::
  :::flow-step{label="It becomes a system call" icon="i-lucide-arrow-right-left"}
  A formal request handed to the operating system: here is the data, here is the
  file, please.
  :::
  :::flow-step{label="The kernel checks it" icon="i-lucide-shield-check" highlight}
  Do you own this file? Do you have permission? Does it exist? Is the disk full?
  Any answer can be no.
  :::
  :::flow-step{label="Hardware, then an answer" icon="i-lucide-hard-drive"}
  If everything passes, the operating system talks to the disk and hands you back
  a result. If not, you get an error and nothing happens.
  :::
::

The **kernel** is the core of the operating system — the part that runs in the
privileged mode and does the actual work. That boundary between your code and the
kernel is where most of the errors in your first year come from.

::real-life{title="Address already in use" source="Every developer's first week"}
You run the project. It fails with `EADDRINUSE: address already in use :::3000`.
Nothing on your screen is using port 3000. What happened is that an earlier run
did not exit properly, its process is still alive in the background holding that
port, and the operating system will not hand the same port to two processes. The
fix is to find that process and stop it — which is a terminal command you will
learn in four lessons, and which is unavailable to you through any window on your
screen.
::

## What confuses people here

**"It works on my machine" is nearly always this lesson.** Not magic, not luck.
The other machine has a different operating system, a different version of a
runtime, different file permissions, a different case-sensitivity rule for
filenames, or a different program already holding the port.

::warning{icon="i-lucide-alert-triangle"}
macOS and Windows treat `Applicant.java` and `applicant.java` as the same file.
Linux does not — and the server your code eventually runs on is almost certainly
Linux. Code that imports `./Applicant` while the file is called `applicant.ts`
works perfectly on your laptop and fails on deployment. It is one of the most
common ways a first deployment breaks, and it is an operating system difference,
not a bug in your code.
::

The other confusion is the word "kill". Stopping a process is called killing it,
by everybody, in every workplace. It is not dramatic and it is not a last resort —
you will do it several times a day.

## What you can do now

You can name the four jobs of an operating system, explain the difference between
a program and a process, and describe what actually happens when your code writes
a file. More usefully: when something refuses to run, you now know there is a
component whose entire job is refusing, and that its refusals have reasons you
can look up.

## Your turn

Open whatever your system calls its task manager or activity monitor — the window
that lists what is running. Then:

1. Count the processes. Guess first, then look. Most people guess low by a factor
   of ten.
2. Find one process you did not knowingly start, and work out what it belongs to.
3. Open a second window of your browser. Does the process count go up by one, or
   by more? Why might a browser be several processes rather than one?

It is good because it is the same mechanism that stops any other program on the machine writing to your files — a rule that only ever protects you is not a rule.   - label: "Interviewers ask this — what is the difference between a program and a process?"
    icon: i-lucide-briefcase
    content: A program is the file on disk — inert instructions. One program can have many processes running at once, and each is isolated from the others. This is a warm-up question in almost every operating-systems round, and the follow-up is usually threads.
