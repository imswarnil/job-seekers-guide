## Why this matters in a job

Because the illusion the OS maintains — that your program has its own memory and
its own processor — is the illusion that breaks under load. Every production
performance problem is a place where you can see through it.

## The job description

An operating system is a program with four jobs:

1. **Share the CPU** between programs that all want it at once.
2. **Share the memory**, and stop one program reading another's.
3. **Talk to hardware** so your program does not have to know what kind of disk it is.
4. **Enforce the rules** — who may open which file, who may kill which process.

You already met the boundary where your program asks the OS for something: the
**system call**. Everything in this course happens on one side or the other of
that line.

## The two worlds

| | User mode | Kernel mode |
| --- | --- | --- |
| Who runs here | Your application | The OS core |
| May touch hardware | No | Yes |
| A crash here | Kills one program | Kills the machine |

Switching between them is cheap but not free, which is why a program that makes
millions of tiny system calls is slower than one that makes fewer, larger ones.
That single fact explains buffered I/O, which you will otherwise meet as an
arbitrary rule.

## The admissions example

Our admissions portal takes 1,420 applications. Behind it:

- The web server is a **process** — an instance of a program, with its own memory.
- Each request is handled by a **thread** — a strand of execution inside that process, sharing its memory.
- The database is a separate process, on a separate machine, with its own everything.

That is why two application processes cannot corrupt each other's memory, and
why two threads absolutely can. Threads sharing memory is what makes them fast
and what makes concurrency hard.

::tip{icon="i-lucide-lightbulb"}
Process: isolation, expensive to create, safe. Thread: sharing, cheap to create,
dangerous. Almost every design question in this area is that trade being made
one more time.
::

## The interview question this answers

**"What is the difference between a process and a thread?"**

A process is an instance of a running program with its own memory space; a thread
is a unit of execution inside a process, sharing that memory with the other
threads. Processes are isolated and costlier to create; threads are cheap and
must coordinate carefully because they share state.
