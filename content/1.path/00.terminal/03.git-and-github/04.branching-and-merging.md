You can, and it is the feature Git is really built around. A **branch** is a
second line of commits growing out of the first, so you can rewrite the report
script completely while the working version sits untouched, one command away.

## Why this matters in a job

Because this is how every professional team works, without exception. Nobody
commits directly to the main line. You branch, you work, you open a pull request,
somebody reviews it, it merges. If you have never made a branch, you have not
seen how software is actually built — and that gap shows up in the first week
rather than the interview.

## What a branch actually is

Not a copy of the folder. Git keeps one set of commits, and a branch is a movable
label pointing at one of them. That is why creating one is instant even on a huge
project.

::flow{numbered direction="vertical" caption="Two lines of work from the same starting point."}
  :::flow-step{label="main, three commits in" icon="i-lucide-git-commit-horizontal"}
  Project set up, applicant data added, report script working. This is what you
  would show somebody today.
  :::
  :::flow-step{label="A branch off the third commit" icon="i-lucide-git-branch" highlight}
  `rewrite-report`. Same history behind it, and from here the two lines diverge.
  :::
  :::flow-step{label="Commits on the branch" icon="i-lucide-file-pen"}
  Two commits rewriting the script. `main` has not moved and still works.
  :::
  :::flow-step{label="Merge back" icon="i-lucide-git-merge"}
  When it works, the branch's commits join `main`. If it never works, delete the
  branch and nothing was lost.
  :::
::

## Making one

```bash [Terminal]
git switch -c rewrite-report
```

```text [Output]
Switched to a new branch 'rewrite-report'
```

`switch -c` creates a branch and moves to it. You will also see
`git checkout -b`, which does the same thing — `checkout` is the older command
that does several unrelated jobs, and `switch` was introduced to separate them.
Both work; `switch` is clearer.

```bash [Terminal]
git branch
```

```text [Output]
  main
* rewrite-report
```

The asterisk is where you are. `git status` says it too, on the first line, which
is one more reason to run it constantly.

Now work normally. Edit, `git add`, `git commit` — every commit lands on this
branch and `main` does not move.

```bash [Terminal]
git switch main
cat sql/reports/shortlist-by-source.sh
```

The file is back to its old contents. Not a copy, not an undo — Git has replaced
the working directory with the state of `main`. Switch again and your new version
returns. Two versions, one folder, no `report-v2-FINAL`.

::warning{icon="i-lucide-alert-triangle"}
Commit before you switch. Uncommitted changes come with you to the other branch,
which is occasionally handy and usually confusing. If you are not ready to
commit, `git stash` puts them aside — and that is the next lesson.
::

## Merging

Get the work back into `main`. Go to the branch you want to merge *into*, then
merge the other one in.

```bash [Terminal]
git switch main
git merge rewrite-report
```

```text [Output]
Updating 3f7a1c9..9b2e4d1
Fast-forward
 sql/reports/shortlist-by-source.sh | 14 ++++++++------
 1 file changed, 8 insertions(+), 6 deletions(-)
```

"Fast-forward" means `main` had not moved at all, so Git simply slid the label
forward. Nothing to reconcile.

```bash [Terminal]
git branch -d rewrite-report
```

Delete the branch once it is merged. Branches are cheap and disposable; leaving
dozens of dead ones around is untidy rather than dangerous.

## The conflict

Here is the thing everybody is nervous about. It happens when two branches change
**the same lines of the same file**, and Git will not guess which one you meant.

```bash [Terminal]
git merge fix-report
```

```text [Output]
Auto-merging sql/reports/shortlist-by-source.sh
CONFLICT (content): Merge conflict in sql/reports/shortlist-by-source.sh
Automatic merge failed; fix conflicts and then commit the result.
```

Nothing is broken and nothing is lost. Git has paused and put both versions into
the file for you to choose between:

```bash [Terminal]
cat sql/reports/shortlist-by-source.sh
```

```text [Output]
<<<<<<< HEAD
grep SHORTLISTED applicants.csv | cut -d, -f6 | sort | uniq -c | sort -rn
=======
tail -n +2 applicants.csv | grep SHORTLISTED | cut -d, -f6 | sort | uniq -c
>>>>>>> fix-report
```

Three markers, and they mean exactly one thing each:

::feature-list{columns="3"}
  :::feature{icon="i-lucide-arrow-up" title="Above the ======="}
  What is on the branch you are merging **into** — `HEAD`, where you are standing.
  :::
  :::feature{icon="i-lucide-minus" title="The ======="}
  The divider. Not part of anybody's code.
  :::
  :::feature{icon="i-lucide-arrow-down" title="Below it"}
  What is on the branch you are merging **in** — named on the last marker line.
  :::
::

Resolving is editing the file until it is what you want, deleting all three
marker lines, then:

```bash [Terminal]
git add sql/reports/shortlist-by-source.sh
git commit -m "Merge fix-report: keep the header strip and the sort"
```

That is the whole procedure. The mistake beginners make is not the editing — it
is leaving a `>>>>>>>` line in the file and committing it, which produces an
error message with no obvious cause an hour later.

::tip{icon="i-lucide-lightbulb"}
The answer is often neither side. The best resolution here takes the header strip
from one and the final sort from the other, because the two people fixed
different halves of the same problem. Read both, then write the right one.
::

If it goes badly wrong:

```bash [Terminal]
git merge --abort
```

Puts everything back exactly as it was before you started the merge. Knowing this
exists is what makes the whole thing unfrightening.

## How teams actually use this

::compare{caption="Two ways of working, and only one of them is employable."}
  :::compare-side{label="Committing to main" verdict="wrong"}
  Every change goes straight onto the line everybody depends on. Nothing is
  reviewed before it lands, and a broken commit breaks it for everyone.
  :::
  :::compare-side{label="A branch per change" verdict="right"}
  A short-lived branch per feature or fix, pushed, opened as a pull request,
  reviewed, merged, deleted. Main is always in a working state.
  :::
::

A **pull request** is GitHub's wrapper around the merge: it shows the diff, lets
people comment on specific lines, and merges when approved. It is where most of
the discussion in a software team happens, and where you will get most of your
early feedback. Practise it on your own repository, alone — branch, push, open a
PR, review your own diff, merge. It feels silly and it is exactly the loop you
will be dropped into.

```bash [Terminal]
git push -u origin rewrite-report
```

Push a branch and GitHub offers to open the pull request for you.

## What confuses people here

**Merging is directional.** `git merge feature` while on `main` brings the
feature into main. Doing it the other way round is a real operation with a real
meaning, and it is not what you wanted.

**A conflict is not an error.** It is a question. Nothing is corrupted, nothing is
lost, and `--abort` is always available.

## What you can do now

You can work on something risky without endangering what works, put it back when
it is ready, throw it away when it is not, and resolve a conflict by reading it
rather than panicking at it.

## Your turn

In your `universityos` repository:

1. On `main`, commit anything outstanding. Confirm with `git status`.
2. Branch `add-fee-report`. Write `sql/reports/fees-by-program.sh` — any pipeline
   over `applicants.csv`. Commit it.
3. Switch back to `main` and `ls sql/reports`. Your new file is not there. Sit
   with that for a second.
4. Merge the branch, confirm the file is back, and delete the branch.
5. Now cause a conflict on purpose. Branch `edit-readme`, change the first line
   of the README, commit. Switch to `main`, change the same line differently,
   commit. Merge.
6. Read the markers. Resolve it into something better than either version.
   Commit.
7. Push everything, and look at the history on GitHub.

    icon: i-lucide-briefcase
    content: It happens when two branches change the same lines of the same file and Git cannot decide which version is correct, so it stops and writes both into the file between conflict markers. You resolve it by editing the file into the version you actually want — often a combination of the two — deleting the markers, staging the file and committing. `git merge --abort` backs out entirely if you would rather start again. What they are checking is whether conflicts scare you, because somebody who fears them avoids branching, and somebody who avoids branching cannot work on a team.
