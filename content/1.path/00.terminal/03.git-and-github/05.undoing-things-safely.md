Almost never. That is the honest answer, and it is the reason this whole chapter
exists — Git keeps far more than you think, and most "I've lost everything"
moments are four minutes from being fixed if you know which command to reach for.

## Why this matters in a job

Because the day you need this, you will be stressed, and the wrong command run in
that state is how a recoverable mistake becomes a real one. Learn the difference
between the four now, calmly, on a repository that does not matter.

## Which one you need

The commands look interchangeable and are not. Find your situation first.

| What happened | What to use | Destroys anything? |
| --- | --- | --- |
| Edited a file, want the last committed version back | `git restore <file>` | Yes — your edits |
| Staged something you did not mean to | `git restore --staged <file>` | No |
| Last commit message is wrong | `git commit --amend` | Rewrites that commit |
| A commit is bad and it is already pushed | `git revert <hash>` | No — adds a new commit |
| Want to move the branch back, keeping the work | `git reset --soft <hash>` | No |
| Want to move back and throw the work away | `git reset --hard <hash>` | **Yes. Permanently** |
| Not ready to commit, need to switch branches | `git stash` | No |

## Undoing an edit

```bash [Terminal]
git restore applicants.csv
```

Throws away your uncommitted changes to that file and puts back the committed
version.

::caution{icon="i-lucide-shield-alert"}
This one genuinely destroys work, and it is the most dangerous command on this
page precisely because it looks harmless. Changes that were never committed were
never recorded anywhere — Git cannot bring them back, because it never had them.
Check `git diff` before you restore, every time.
::

```bash [Terminal]
git restore --staged applicants.csv
```

Different job entirely: takes the file out of the staging area and leaves your
edits alone. Safe.

## Fixing the last commit

```bash [Terminal]
git commit --amend -m "Add shortlist report, grouped by source"
```

Replaces the previous commit with a new one. Use it for a bad message or a file
you forgot to include, **before you push**.

::warning{icon="i-lucide-alert-triangle"}
Amending after pushing rewrites history that other people may already have. Their
Git will disagree with yours, and the only way to reconcile is a force push,
which is the section at the bottom of this page. The rule is simple: amend freely
before pushing, never after.
::

## Undoing a commit that is already shared

```bash [Terminal]
git log --oneline
```

```text [Output]
9b2e4d1 Add fee report
3f7a1c9 Add applicant CSV and shortlist report
a10c8e7 Set up the project structure
```

```bash [Terminal]
git revert 9b2e4d1
```

Creates a **new** commit that undoes what that one did. The original stays in the
history, and so does the fact that you reversed it.

This is the correct tool for anything already pushed. It is honest — the history
shows what happened and what was done about it — and it is safe, because nothing
anybody else has is invalidated.

::compare{caption="Undoing a bad commit that other people already have."}
  :::compare-side{label="reset --hard, then force push" verdict="wrong"}
  The commit vanishes from your copy and you overwrite the shared branch. Anybody
  who had pulled now has commits that officially do not exist, and their next
  push either fails or re-adds them.
  :::
  :::compare-side{label="revert" verdict="right"}
  A new commit reverses the change. Everyone pulls normally. The history is
  longer and completely truthful, which is what history is for.
  :::
::

## Moving the branch backwards

`reset` moves the branch label to an earlier commit. What happens to your work
depends entirely on the flag, and this is the distinction to actually memorise.

::flow{numbered direction="vertical" caption="Three resets to the same commit, three very different outcomes."}
  :::flow-step{label="--soft" icon="i-lucide-inbox"}
  Branch moves back. All the changes from the undone commits are kept, and
  staged. Use it to recombine three messy commits into one good one.
  :::
  :::flow-step{label="--mixed (the default)" icon="i-lucide-file-pen"}
  Branch moves back. Changes are kept in your working directory but unstaged.
  :::
  :::flow-step{label="--hard" icon="i-lucide-flame" highlight}
  Branch moves back and **every change is destroyed** — commits, staged work and
  uncommitted edits alike. No prompt.
  :::
::

```bash [Terminal]
git reset --soft HEAD~1
```

`HEAD~1` means "one commit before where I am". This undoes the last commit and
leaves its changes staged, ready to be committed properly. It is genuinely useful
and completely safe.

```bash [Terminal]
git reset --hard HEAD~1
```

::caution{icon="i-lucide-skull"}
**`git reset --hard` throws away uncommitted work with no confirmation and no
bin.** The commits themselves can usually be recovered — see the next section —
but changes you had not committed cannot, because they were never recorded.

Two rules that will save you: commit before any reset, even a rubbish commit you
intend to tidy up; and never type `--hard` while stressed. There is no situation
where the extra thirty seconds is expensive.
::

## The safety net almost nobody knows

You reset hard, and the commits are gone from `git log`. They are not gone from
Git.

```bash [Terminal]
git reflog
```

```text [Output]
9b2e4d1 HEAD@{0}: reset: moving to HEAD~1
c4d9f22 HEAD@{1}: commit: Add fee report by program
9b2e4d1 HEAD@{2}: commit: Add shortlist report
3f7a1c9 HEAD@{3}: commit: Set up the project structure
```

`reflog` is a log of everywhere `HEAD` has been — every commit, switch, merge and
reset, including the ones no longer reachable from any branch. Your "lost" commit
is on that list.

```bash [Terminal]
git reset --hard c4d9f22
```

Back. Commits are kept for around ninety days before being cleaned up, so almost
anything committed is recoverable for months.

::tip{icon="i-lucide-lightbulb"}
This is the answer to "I've destroyed everything". Take a breath, run
`git reflog`, find the last good hash. It works far more often than people
expect, and knowing about it is a small piece of professional confidence you can
now claim honestly.
::

## Putting work aside

```bash [Terminal]
git stash
```

Takes your uncommitted changes, saves them somewhere separate, and leaves you
with a clean working directory. For the moment when something urgent needs doing
on another branch and you are mid-thought.

```bash [Terminal]
git stash list
git stash pop
```

`pop` brings the most recent stash back and removes it from the list. Stashes are
easy to forget about — three weeks later you have five and no idea what is in
them — so treat it as a tool for the next twenty minutes, not for storage.

## The one that ends friendships

```bash [Terminal]
git push --force
```

::caution{icon="i-lucide-skull"}
**This replaces the remote branch's history with yours, deleting any commits it
has that you do not.** On a shared branch, those commits are somebody else's
work, and they are gone from the remote without warning or record.

If you genuinely must rewrite a branch you own, use `--force-with-lease` instead.
It refuses when the remote has moved since you last fetched — which is exactly
the case where forcing would destroy something. Most teams block force pushes to
`main` entirely, and are right to.
::

The honest version of the rule: rewrite history freely on your own unpushed
branch, and never on anything anybody else might have pulled.

## What you can do now

You can undo an edit, unstage a file, fix a bad message, reverse a shared commit
safely, move a branch backwards deliberately, park work mid-thought, and recover
commits you thought you had destroyed. Which means the fear is gone, and that was
the point of the entire chapter.

## Your turn

Do all of this on your `universityos` repository. Every step is recoverable, and
step 5 is the one worth doing slowly.

1. Change three lines in the README, look at `git diff`, then restore the file.
2. Stage `applicants.csv`, then unstage it without losing the changes.
3. Make a commit with a deliberately bad message, then amend it into a good one.
4. Commit something you do not want, push it, then revert it. Look at the log —
   there should be two commits, not zero.
5. Commit something, `git reset --hard HEAD~1` to destroy it, then get it back
   with `git reflog`. This is the exercise.
6. Start editing a file, `git stash`, switch branches, come back and `git stash
   pop`.
