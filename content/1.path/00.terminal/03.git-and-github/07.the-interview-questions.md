The one is `merge` versus `rebase`, and the reason people fumble it is that they
explain what each does — which is not what was asked. The question is when you
would use which, and there is a rule.

## Why this matters in a job

Because Git is on every job description at every level, which means it is on
every interview, which means these five come up more often than anything about
data structures. They are also the cheapest marks available: you did all of this
yesterday.

## The five

::accordion
---
items:
  - label: What is the difference between Git and GitHub?
    icon: i-lucide-message-circle-question
    content: "Git is the version control system, running on your machine, with the full history locally and no network required. GitHub is a hosting service for Git repositories that adds collaboration — pull requests, reviews, issues, permissions, automation. GitLab and Bitbucket do the same job. What they are checking — an alarming number of people who list Git have only used a website, and this question finds them in ten seconds."
  - label: What is the staging area for?
    icon: i-lucide-message-circle-question
    content: "It lets you choose which of your current changes go into the next commit, so a commit is one coherent idea instead of an afternoon's worth of unrelated work. That matters because single-purpose commits can be reviewed, reverted and bisected, and 'update' cannot. What they are checking — whether you understand why the extra step exists, rather than treating `git add` as a word you type before `git commit`. Mentioning `git add -p` for splitting work you have already done is a genuine differentiator."
  - label: How do you undo a commit that is already pushed?
    icon: i-lucide-message-circle-question
    content: "`git revert <hash>` — it creates a new commit that undoes the old one, leaving the history intact so nobody else's copy is invalidated. Resetting and force-pushing would delete commits other people may already have, which is why it is the wrong answer for anything shared. What they are checking — whether you think about other people's copies at all. The rule to say out loud: rewrite history freely before pushing, never after."
  - label: Merge or rebase?
    icon: i-lucide-message-circle-question
    content: "Merge preserves what actually happened and produces a merge commit; rebase replays your commits on top of the target branch and produces a straight line, at the cost of rewriting your commits into new ones. My rule: rebase my own unpushed branch to tidy it before review, merge everything else, and never rebase anything anybody else has pulled. What they are checking — that you answer with a decision and a boundary rather than two definitions. Teams differ on this and there is no universally correct answer, so having a defensible position matters more than which one you pick."
  - label: You have committed a password. What now?
    icon: i-lucide-message-circle-question
    content: "Rotate the credential first — assume it is compromised, because on a public repository automated scanners find keys within minutes. Only then deal with Git: removing it from the history requires rewriting and a coordinated force push, and deleting it in a later commit does nothing at all, because the old commit still contains it. Then `.gitignore` the file so it cannot happen again. What they are checking — that you identify which half of this is the emergency. Candidates who go straight to the Git surgery have got the priority backwards."
---
::

## The one behind all of them

Not really a Git question, and it is asked constantly:

::compare{caption="'Walk me through how you work on a change.'"}
  :::compare-side{label="Never worked in a team" verdict="wrong"}
  "I write the code and commit it." Nothing about branches, review, or how it
  reaches anybody else — which tells the interviewer everything about the size of
  project you have worked on.
  :::
  :::compare-side{label="Has seen how it is done" verdict="right"}
  "Pull main, branch off it, small commits as I go, push the branch, open a pull
  request, address the review comments, squash or merge, delete the branch."
  :::
::

You can honestly give the second answer after this chapter, because you have done
every step of it — on your own repository, reviewing your own pull request, which
feels absurd and is exactly the right practice.

## Your turn

Say all five out loud with the page closed. For the fourth one, do not stop at
the definitions — finish with a rule you would actually follow, and be ready to
say why.

Then open your `university-management-app` repository on GitHub and read your own history as a
stranger would. Do the messages say what changed? Could you find the commit that
added the fee report in ten seconds? That history is a work sample, and it is
already public.
