You get there with one command, and the disorienting part is that nothing looks
different afterwards. Same black rectangle, same `pwd` and `ls` — except the
machine answering is two thousand miles away and has never had a screen attached
to it.

## Why this matters in a job

Because that is where your code runs. Not on your laptop: on a machine you have
never seen, with no desktop, no icons and no mouse, which you reach entirely
through the commands in the last four lessons. Everything you have practised was
preparation for this, and the reason a graphical interface was never enough.

::real-life{title="Why the terminal is not optional" source="A first on-call rotation"}
The site is down. You are on a phone, connected to a laptop, connected to a
server in Frankfurt. There is no interface. There is a prompt, a log file, and
`tail -f`. Everybody who has ever been in that situation was glad they knew the
last four lessons, and nobody has ever been in it wishing they had spent longer
in a file browser.
::

## Getting there

```bash [Terminal]
ssh swarnil@203.0.113.42
```

```text [Output]
The authenticity of host '203.0.113.42' can't be established.
ED25519 key fingerprint is SHA256:pW9K…8sQ.
Are you sure you want to continue connecting (yes/no)?
```

SSH — secure shell. The pattern is `ssh user@machine`, where the machine is an
address or a name. That first-connection question is the machine saying "you have
never met me; here is my fingerprint". Say yes once and it is remembered; if it
ever asks again for a machine you know, something has changed and it is worth
finding out what before you answer.

Then you are in:

```text [Output]
Welcome to Ubuntu 24.04.1 LTS
swarnil@universityos-prod:~$
```

Look at the prompt. Different user, different machine name. Everything you type
now happens there — `ls`, `cd`, `grep`, `tail -f`, all of it, identical. This is
why the last four lessons were worth typing rather than reading.

`exit`, or `Ctrl + D`, brings you home.

## Keys, not passwords

Typing a password into every connection is slow and, more importantly, a password
can be guessed at scale. The professional way is a **key pair**: two matched
files, one secret and one public.

::flow{numbered caption="How key authentication works, and why it is safer than a password."}
  :::flow-step{label="You generate a pair" icon="i-lucide-key-round"}
  A private key that never leaves your machine, and a public key that is safe to
  hand out.
  :::
  :::flow-step{label="The public half goes to the server" icon="i-lucide-upload"}
  Or to GitHub, or anywhere else you want to prove who you are.
  :::
  :::flow-step{label="The server sets a challenge" icon="i-lucide-puzzle"}
  Something only the holder of the matching private key could answer.
  :::
  :::flow-step{label="You are in, with nothing sent" icon="i-lucide-shield-check" highlight}
  The private key never crosses the network. There is no password to intercept
  and none to guess.
  :::
::

```bash [Terminal]
ssh-keygen -t ed25519 -C "swarnil@example.com"
```

```text [Output]
Generating public/private ed25519 key pair.
Enter file in which to save the key (/Users/swarnil/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
```

Press enter for the location. **Do set a passphrase** — it encrypts the private
key on disk, so a stolen laptop is not a stolen identity.

You now have two files:

```bash [Terminal]
ls -l ~/.ssh
```

```text [Output]
-rw-------  1 swarnil  staff   464 19 Aug 13:10 id_ed25519
-rw-r--r--  1 swarnil  staff   108 19 Aug 13:10 id_ed25519.pub
```

Look at the permissions, and notice they are exactly the lesson before this one.
The private key is `600` — nobody but you, not even read. SSH refuses to use a
private key with looser permissions than that, which is the tool enforcing the
rule for you.

::caution{icon="i-lucide-shield-alert"}
**The file without `.pub` is the secret one.** Never paste it anywhere, never
commit it, never email it. The `.pub` file is the one that goes to servers and to
GitHub. People mix these up under time pressure, and pasting a private key into a
web form means generating a new pair and revoking the old one immediately.
::

You will use this exact key in two lessons' time, to connect to GitHub. It is the
same mechanism.

## The network, without a browser

Two tools worth having now.

```bash [Terminal]
ping example.com
```

```text [Output]
PING example.com (93.184.215.14): 56 data bytes
64 bytes from 93.184.215.14: icmp_seq=0 ttl=53 time=118.4 ms
64 bytes from 93.184.215.14: icmp_seq=1 ttl=53 time=117.9 ms
```

"Is this machine reachable, and how long does a round trip take?" `Ctrl + C` to
stop. It answers one specific question — reachability — and answers nothing about
whether the application on it is working.

```bash [Terminal]
curl https://example.com
```

Fetches a URL and prints the response. A browser with no window, which makes it
the tool for asking an application a question directly:

```bash [Terminal]
curl -i https://example.com
```

```text [Output]
HTTP/2 200
content-type: text/html; charset=UTF-8
content-length: 1256

<!doctype html>
…
```

`-i` includes the response headers. That `200` is a status code — the server
saying "fine, here it is". You will meet the rest of them properly in the HTML
track; for now, 200 is good, 404 means no such thing, 500 means the server broke.

::tip{icon="i-lucide-lightbulb"}
This is how you find out whether "the site is down" means the machine is
unreachable, the application has crashed, or the browser is showing a cached
page. `ping` answers the first, `curl -i` answers the second, and the difference
is the first thing anyone will ask you.
::

## What confuses people here

**"Connection refused" and "connection timed out" are different failures.**
Refused means something answered and said no — the machine is there, nothing is
listening on that port. Timed out means nothing answered at all — wrong address,
machine down, or a firewall silently dropping you. The first is usually your
application; the second is usually the network.

**Nothing you do locally affects the server, and nothing on the server affects
you.** Two separate machines, two separate filesystems. Editing a file on your
laptop changes nothing in Frankfurt until you deliberately send it — which is
what the whole next chapter is about.

## What you can do now

You can reach a machine you do not own, work on it with everything you already
know, generate a key pair and explain why it is safer than a password, and ask a
web server a direct question without opening a browser.

## Your turn

You may not have a server yet. All of this still works.

1. Generate an SSH key pair if you do not have one. Check `ls -l ~/.ssh` and read
   the permissions on both files.
2. Run `ping github.com` and stop it after five replies. What is your round-trip
   time?
3. `curl -i https://github.com` — find the status code in the first line.
4. `curl -i https://github.com/this-page-does-not-exist` — what changed?
5. `ssh git@github.com`. It will refuse you a shell. Read what it says.

---
items:
  - label: What is the difference between "connection refused" and "connection timed out", and what does each one point at?
    icon: i-lucide-circle-help
    content: Refused means the machine answered and actively rejected the connection — it is up, and nothing is listening on that port. That usually means your application is not running. Timed out means nothing answered at all — the wrong address, a machine that is down, or a firewall dropping packets silently. That usually means the network or the host, not your code. Knowing which is which saves an hour of looking in the wrong place.
  - label: "Interviewers ask this — why is SSH key authentication considered safer than a password?"
    icon: i-lucide-briefcase
    content: Because the secret never crosses the network. The server issues a challenge that only the holder of the private key can answer, so there is nothing to intercept and nothing to guess — and keys are long enough that brute force is not on the table. The private key can also be protected with a passphrase, so a stolen laptop is not immediately a stolen identity. The follow-up is usually about rotating and revoking keys, which is the honest weak point: an old key left on a server stays valid until somebody removes it.
