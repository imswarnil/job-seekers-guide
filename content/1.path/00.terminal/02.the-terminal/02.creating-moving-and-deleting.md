The command that throws things away is `rm`, and it does not move anything to a
bin. It unlinks the file, the operating system marks the space as reusable, and
there is no undo, no confirmation and no dialog box. So that one gets a warning
before it gets an explanation.

## Why this matters in a job

Because you will be creating and moving files all day, every day, and because the
story of somebody deleting the wrong thing is one every team has. Mine cost me
four hours of unbacked-up work in my second week, and it taught me the habit that
this lesson is really about: **look before you destroy.**

## Making things

```bash [Terminal]
mkdir universityos
```

Make directory. No output means it worked — a quiet terminal is a successful
terminal, and the sooner you stop expecting congratulation the better.

```bash [Terminal]
mkdir -p universityos/java-tools/src
```

`-p` means "make the parents too". Without it, that command fails if
`universityos/java-tools` does not already exist. With it, the whole chain is
created in one go.

```bash [Terminal]
touch universityos/README.md
ls universityos
```

```text [Output]
README.md    java-tools
```

`touch` creates an empty file if it does not exist. Its actual purpose is
updating a file's timestamp, which nobody uses it for.

::warning{icon="i-lucide-alert-triangle"}
Do not put a space in the folder name. `university os` is legal and every command
you type about it afterwards has to quote it or escape the space, forever. Use
hyphens. This is a small decision that annoys people for years.
::

## Copying and moving

```bash [Terminal]
cp README.md notes/README-backup.md
```

Copy: source first, destination second. Every command in this family takes that
order.

```bash [Terminal]
cp -r java-tools java-tools-old
```

`-r` means recursive — go into the folder and copy everything inside it. Copying
a folder without `-r` fails, and the error says so.

```bash [Terminal]
mv notes/README-backup.md notes/backup.md
```

Move. And here is the thing nobody tells you: **`mv` is also how you rename.**
Moving a file to a new name in the same folder is a rename, because a name is
just where a file sits in the tree.

```bash [Terminal]
mv backup.md notes/
```

If the destination is an existing folder, the file goes into it keeping its name.
If it is not, the file is renamed to that. Same command, two behaviours, and the
difference is whether the destination exists.

::warning{icon="i-lucide-alert-triangle"}
`mv` and `cp` overwrite the destination silently if it already exists. No prompt.
`cp -i` and `mv -i` ask first, and are worth adding to your muscle memory before
the day you need them.
::

## Deleting, carefully

Read this section before you type anything in it.

```bash [Terminal]
rm notes/backup.md
```

Gone. Not in a bin. Not recoverable through any normal means.

```bash [Terminal]
rm java-tools-old
```

```text [Output]
rm: java-tools-old: is a directory
```

`rm` refuses folders by default, which is a kindness. To remove a folder and its
contents you need `-r`:

```bash [Terminal]
rm -r java-tools-old
```

And then there is the one everybody has heard of.

::caution{icon="i-lucide-skull"}
**`rm -rf` deletes a folder, everything in it, and everything below that, without
asking and without stopping for errors.** The `f` means force: it will not warn
you, it will not confirm, and it will not tell you what it removed.

Three rules, all of which I learned by breaking one of them:

1. **Run `ls` on the exact path first.** Look at what you are about to remove.
2. **Never use a wildcard and `-rf` in the same command.** `rm -rf *` in the wrong
   folder is how people lose a day.
3. **Type the path, do not paste it.** Half a pasted path — the half before a
   stray newline — has ended careers. `rm -rf /` and `rm -rf ~` are the two
   famous ones.
::

There is no recycle bin here because there is no desktop here. The graphical bin
is a feature of the desktop software, not of the filesystem, and the terminal is
below that layer.

::real-life{title="The deploy script that deleted the wrong folder" source="A small team, a Friday"}
A cleanup script ran `rm -rf $BUILD_DIR/` where `BUILD_DIR` was set from an
environment variable. On the server, the variable was empty. The command became
`rm -rf /` with a trailing slash, ran as root, and the machine did exactly as it
was told for about ninety seconds. The lesson everyone took away was not "avoid
rm"; it was "quote your variables and check they are set" — and it is why you
will see `${BUILD_DIR:?}` in careful scripts, which refuses to run when the
variable is empty.
::

## What confuses people here

**A quiet terminal means success.** Beginners retype a command because nothing
happened. Something happened; Unix tools only speak when there is a problem or
when you asked for output.

**Order is always source then destination**, for `cp`, `mv` and nearly everything
else. When a command mysteriously does the opposite of what you wanted, check
that first.

  - label: "`mv report.sql reports/` and `mv report.sql reports` — one of these behaves differently depending on the state of the machine. Which, and how?"

If it does not, the file is renamed to `reports` — an ordinary file with no extension, which then confuses everything downstream. The trailing slash in the first version makes your intent explicit and turns a silent surprise into an error. That is why careful scripts always write the slash.
  - label: "Interviewers ask this — what does `rm -rf` do, and when would you use it?"
    icon: i-lucide-briefcase
    content: It removes a path recursively and without prompting — folder, contents, and everything beneath, ignoring errors. You use it for things you are certain are disposable, most often build output or `node_modules`, and you check the path with `ls` first. The answer they are listening for is caution without theatre: somebody who says "never use it" has not worked on a real project, and somebody who uses it casually will eventually cost the team a day.
