The kernel is stopping you, on the authority of the file's owner and its
permission bits. "Permission denied" is not a fault — it is the operating system
working correctly, and telling you so in three words.

## Why this matters in a job

Two reasons, and you will hit both in your first month. Scripts that will not run
until you make them executable. And a server where you are one user among several
and the difference between your files, the application's files and the system's
files is enforced rather than suggested.

The third reason is that the reflex people develop instead — putting `sudo` in
front of everything until the error goes away — creates files owned by the wrong
user, which breaks in ways that take a day to unpick.

## Who you are

```bash [Terminal]
whoami
```

```text [Output]
swarnil
```

```bash [Terminal]
id
```

```text [Output]
uid=501(swarnil) gid=20(staff) groups=20(staff),12(everyone),61(localaccounts)
```

You are a user with a numeric id, and you belong to one or more **groups**.
Every file on the machine is owned by a user and a group, and permissions are
expressed in terms of three audiences: the owner, the group, and everybody else.

## Reading the ten characters

That string at the start of every `ls -l` line is not decoration.

```bash [Terminal]
ls -l
```

```text [Output]
drwxr-xr-x   5 swarnil  staff   160 19 Aug 09:14 sql
-rw-r--r--   1 swarnil  staff  4210 19 Aug 11:47 applicants.csv
-rwxr-xr-x   1 swarnil  staff   812 19 Aug 11:52 backup.sh
```

Take `-rwxr-xr-x` apart. One character, then three groups of three:

::memory{kind="array" caption="The ten characters of a permission string, in the order they appear."}
---
cells:
  - { value: "-", label: "type" }
  - { value: "r", label: "owner" }
  - { value: "w", label: "owner" }
  - { value: "x", label: "owner", state: "active" }
  - { value: "r", label: "group" }
  - { value: "-", label: "group" }
  - { value: "x", label: "group" }
  - { value: "r", label: "other" }
  - { value: "-", label: "other" }
  - { value: "x", label: "other" }
---
::

- **Character 1** — the type. `d` for directory, `-` for a normal file, `l` for a
  link.
- **Characters 2–4** — what the **owner** may do.
- **Characters 5–7** — what members of the **group** may do.
- **Characters 8–10** — what **everyone else** may do.

And in each group of three: `r` read, `w` write, `x` execute. A dash means not
allowed.

So `-rw-r--r--` on `applicants.csv` reads: an ordinary file, the owner may read
and change it, everybody else may only read it. And `-rwxr-xr-x` on `backup.sh`
adds execute — this one can be run as a program.

::warning{icon="i-lucide-alert-triangle"}
On a **directory**, `x` does not mean execute. It means "may enter and traverse".
A folder with `r` but no `x` lets you list the names inside and not open any of
them, which produces baffling errors until you know this. It is the single
weirdest corner of the permission model and it comes up in interviews for exactly
that reason.
::

## Changing them

```bash [Terminal]
chmod +x backup.sh
```

Change mode. `+x` adds execute for everyone; `chmod u+x` adds it for the owner
only. This is the command you will actually use most, because a script you have
just written or downloaded is not executable until you say so.

You will also see the numeric form, and you should be able to read it:

| Number | Bits | Means |
| --- | --- | --- |
| 7 | `rwx` | read, write, execute |
| 6 | `rw-` | read, write |
| 5 | `r-x` | read, execute |
| 4 | `r--` | read only |
| 0 | `---` | nothing |

Three digits, one per audience. `chmod 755 backup.sh` is owner everything, group
and others read and execute — the normal setting for a script. `chmod 644
applicants.csv` is owner read and write, everybody else read — the normal
setting for a file.

::caution{icon="i-lucide-shield-alert"}
`chmod 777` gives every user on the machine permission to read, change and run
the file. It is the most common piece of bad advice on the internet, because it
does make the error go away. On a shared machine or a server it is a genuine
security hole, and on a deployment it is the sort of thing that gets flagged in a
review. Work out who needs access and grant that instead.
::

## Being somebody else, briefly

```bash [Terminal]
sudo mkdir /opt/university-management-app
```

`sudo` runs one command as the administrator — the **root** user, who is exempt
from permission checks. It asks for your password, remembers it for a few
minutes, and logs what you did.

::compare{caption="Two responses to the same 'permission denied'."}
  :::compare-side{label="Reach for sudo" verdict="wrong"}
  The command works. The file it creates is now owned by root, so every later
  command that touches it also needs sudo, and the tool you are using breaks in a
  way that looks unrelated a week later.
  :::
  :::compare-side{label="Read the message first" verdict="right"}
  `ls -l` the path. Who owns it? What are its permissions? Nine times out of ten
  you are in the wrong folder, or the file belongs to a previous run that used
  sudo, and the fix is ownership rather than force.
  :::
::

The rule I use: `sudo` is for installing software and for administering the
machine. If you are typing it to work on your own project, something is already
wrong.

## Processes, and stopping them

Your project will not start because something is already using its port. Here is
how you deal with that, and it is the same shape every time.

```bash [Terminal]
ps aux | grep node
```

```text [Output]
swarnil  4821   0.4  1.2  node /Users/swarnil/projects/university-management-app/web/server.js
swarnil  5107   0.0  0.0  grep node
```

`ps aux` lists every running process. The second column is the **process id** —
the number the operating system knows it by, and the only thing you need to stop
it. The second line is your own `grep` catching itself, which is normal and
briefly confusing.

```bash [Terminal]
lsof -i :3000
```

Lists whatever is listening on port 3000, which is the direct answer when the
error was about a port.

```bash [Terminal]
kill 4821
```

Asks the process to shut down cleanly — save what you are doing, close your
files, exit. Nearly always enough.

```bash [Terminal]
kill -9 4821
```

Tells the kernel to stop it immediately. It gets no chance to clean up, so
half-written files stay half-written. Use it when the polite version has been
ignored, and not before.

```bash [Terminal]
top
```

A live view of what is using the processor and memory, updating every second.
`q` to quit. This is where you look when the machine has gone quiet and you want
to know which program is responsible.

::real-life{title="Address already in use, at nine on a Monday" source="Everybody, repeatedly"}
The dev server will not start: `EADDRINUSE :::3000`. Nothing visible is running.
What happened is that Friday's server never exited — the terminal window was
closed but the process was not stopped. Two commands solve it: `lsof -i :3000` to
find the id, `kill` to end it. The developers who know this lose thirty seconds.
The ones who do not restart their laptop.
::

## What you can do now

You can read a permission string on sight, make a script executable, explain what
`sudo` is doing and why reaching for it is usually a mistake, and find and stop
the process that is standing in your way.

## Check yourself

::accordion
---
items:
  - label: A folder has permissions `r--` for you. You can see the filenames inside it but cannot open any of them. Why?
    icon: i-lucide-circle-help
    content: Because on a directory, `r` grants the right to list the names and `x` grants the right to traverse into it and reach what is inside. With read but no execute you get exactly this: a list you cannot act on. `chmod +x` on the directory fixes it. This is the corner of the model that catches nearly everyone, and being able to explain it marks you out immediately.
  - label: "Interviewers ask this — what does `chmod 755` mean, and when would you use it?"
    icon: i-lucide-briefcase
    content: Three digits, one for owner, group and others; each is the sum of read (4), write (2) and execute (1). So 755 is `rwxr-xr-x` — the owner can do everything, everybody else can read and execute. It is the standard setting for a script or a directory. The natural follow-up is 644 for a data file, and the one to volunteer is that 777 is almost never the right answer.
