You do not open a 40,000-line log in an editor. You print the last twenty lines,
or you search it for the word "error", and both of those are one command. This is
the lesson where the terminal stops being a slower Finder and starts being
something a graphical interface cannot do at all.

## Why this matters in a job

Because the answer to "why did the deployment fail?" is one line inside a log
file that nobody can open comfortably, on a machine with no screen. Grep is how
that line gets found, and it is the single most-used tool in this chapter. I use
it every working day and I have never once opened a log in an editor since.

## Printing a file

```bash [Terminal]
cat sql/reports/funnel.sql
```

```text [Output]
SELECT stage, COUNT(*) AS applicants
FROM applications
GROUP BY stage
ORDER BY applicants DESC;
```

`cat` prints the whole file and hands you back the prompt. Perfect for short
files. Catastrophic for a 40,000-line log, which scrolls past for eight seconds
and leaves you staring at the end of it.

Four tools, and the only skill is picking the right one:

| Command | What you get | When |
| --- | --- | --- |
| `cat file` | The whole thing, at once | Files you can read in one screen |
| `less file` | A scrollable view you can search | Anything longer |
| `head -n 20 file` | The first 20 lines | Checking a file's shape or its header row |
| `tail -n 20 file` | The last 20 lines | Logs. The end is where the failure is |

`less` opens a viewer: arrow keys and `Space` to move, `/error` to search
forwards, `n` for the next match, and **`q` to quit**. That last one strands more
beginners than anything else in this chapter — if you are ever stuck in something
that will not take a command, try `q`.

And the one worth knowing before you need it:

```bash [Terminal]
tail -f logs/app.log
```

`-f` means follow. It prints new lines as they are written, so you watch a log
live while you reproduce a bug. `Ctrl + C` stops it. This is what people mean
when they say "tail the logs".

## Finding a line

```bash [Terminal]
grep "SHORTLISTED" applicants.csv
```

```text [Output]
2041,Ananya Rao,B.Tech CSE,87,SHORTLISTED
2078,Meera Nair,B.Sc Maths,91,SHORTLISTED
```

Grep prints every line containing the text. That is all it does, and it is
enough to build a career on. Four flags carry most of the work:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-case-sensitive" title="-i — ignore case"}
  `grep -i "shortlisted"` finds `SHORTLISTED`, `Shortlisted` and `shortlisted`.
  Use it by default when searching human-entered data.
  :::
  :::feature{icon="i-lucide-hash" title="-n — line numbers"}
  Tells you *where* the match is, which is what you actually needed.
  :::
  :::feature{icon="i-lucide-folder-search" title="-r — search a whole folder"}
  `grep -rn "cutoff" .` searches every file below here. This is how you find
  where something is defined in a codebase you have never seen.
  :::
  :::feature{icon="i-lucide-file-x" title="-v — invert"}
  Show the lines that do *not* match. Surprisingly useful for filtering noise out
  of a log.
  :::
::

::real-life{title="How you find your way around a codebase on day one" source="Every developer joining a new team"}
Nobody reads a codebase from the top. Somebody says "the shortlisting rule is
wrong", and the first thing an experienced developer does is `grep -rn "shortlist"
.` from the project root. Thirty seconds later they have five files and a place to
start. This one command is most of what "getting up to speed quickly" actually
looks like.
::

## The idea that makes all of this work

Here is the design decision behind the whole system, made in the 1970s and still
paying out: **every tool does one thing, reads text and writes text, and the
output of one can be fed into the next.** The `|` character — a pipe — is what
joins them.

::flow{numbered caption="Four small tools, one question: which departments do the shortlisted applicants come from?"}
  :::flow-step{label="cat applicants.csv" icon="i-lucide-file-text"}
  Emits every line of the file.
  :::
  :::flow-step{label="grep SHORTLISTED" icon="i-lucide-filter"}
  Keeps only the lines with that word.
  :::
  :::flow-step{label="cut -d, -f3" icon="i-lucide-scissors"}
  Keeps only the third comma-separated column — the programme.
  :::
  :::flow-step{label="sort | uniq -c" icon="i-lucide-list-ordered" highlight}
  Sorts them so identical lines are adjacent, then counts each run.
  :::
::

```bash [Terminal]
cat applicants.csv | grep "SHORTLISTED" | cut -d, -f3 | sort | uniq -c | sort -rn
```

```text [Output]
  42 B.Tech CSE
  31 B.Sc Maths
  19 B.Com
```

That is a report. No program was written, no database was involved, and none of
those five tools knows the others exist. You have just written the same query you
will write in SQL in two tracks' time — `GROUP BY stage` — with four programs and
a pipe.

::tip{icon="i-lucide-lightbulb"}
`uniq -c` only counts *adjacent* duplicates, which is why `sort` always comes
first. Forgetting that is the classic pipeline bug, and the symptom is counts of
1 all the way down.
::

## Sending output somewhere

```bash [Terminal]
grep "REJECTED" applicants.csv > notes/rejected.txt
```

`>` redirects output into a file instead of the screen. **It overwrites without
asking.** `>>` appends instead, which is what you want more often than you think.

```bash [Terminal]
grep -c "REJECTED" applicants.csv >> notes/daily-counts.txt
```

## What confuses people here

::warning{icon="i-lucide-alert-triangle"}
**`>` destroys the destination file's contents before the command even runs.** So
`sort file.txt > file.txt` empties the file — the shell truncates it to zero, then
starts reading. Sorting a file in place needs a temporary file or a tool built for
it. This has caught almost everyone once.
::

The other one is quoting. `grep "B.Tech CSE" file` with the quotes searches for
that phrase; without them, the shell treats `CSE` as a second argument, which
means a file called `CSE`, and you get "No such file or directory" for something
you never asked about. **Quote anything containing a space.**

## What you can do now

You can read any file without an editor, find any line in any file, watch a log
as it happens, and chain small tools into something none of them could do alone.
That last one is the actual skill — the ability to see a question and reach for a
pipeline instead of a program.

## Your turn

Create the file first, so you have something real to search:

```bash [Terminal]
cd ~/projects/universityos
cat > applicants.csv <<'ROWS'
id,name,program,score,status
2041,Ananya Rao,B.Tech CSE,87,SHORTLISTED
2042,Imran Sheikh,B.Tech CSE,74,UNDER_REVIEW
2043,Meera Nair,B.Sc Maths,91,SHORTLISTED
2044,Rohit Verma,B.Com,58,REJECTED
2045,Sana Qureshi,B.Sc Maths,66,UNDER_REVIEW
2046,Dev Patel,B.Tech CSE,79,REJECTED
ROWS
```

Then, without opening an editor:

1. Print the whole file.
2. Print only the header row.
3. Find every shortlisted applicant, with line numbers.
4. Find everyone *not* rejected.
5. Count how many applicants there are, excluding the header.
6. Produce a count of applicants per programme, highest first.
7. Write the rejected rows into `notes/rejected.csv`, then check it worked.

    icon: i-lucide-key
    content: "1. `cat applicants.csv`. 2. `head -n 1 applicants.csv`. 3. `grep -n SHORTLISTED applicants.csv`. 4. `grep -v REJECTED applicants.csv` — note this keeps the header too, which is either a bug or a feature depending on what you wanted. 5. `tail -n +2 applicants.csv | wc -l` gives 6; `wc -l` alone counts the header as well, and quietly answering 7 is exactly the kind of off-by-one that reaches a report. 6. `tail -n +2 applicants.csv | cut -d, -f3 | sort | uniq -c | sort -rn`. 7. `grep REJECTED applicants.csv > notes/rejected.csv` then `cat notes/rejected.csv`. The beginner version of 6 pipes `cat` into `grep` into `cut`; the experienced version drops the `cat` entirely — `grep PATTERN file` already takes a filename — and that habit is worth building, because a pipeline with fewer moving parts has fewer places to be wrong."
