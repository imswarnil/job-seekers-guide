What decides which computation happens next is a counter. A single number, held
in the processor, pointing at the next instruction. Increase it, and the machine
moves on. That is the entire mechanism.

## Why this matters in a job

Because "why is it slow?" and "why did we lose that data?" are the two questions
you will be asked most often in your first two years, and both are answered from
this lesson. One is about how far the processor has to reach for a value. The
other is about which kind of memory the value was sitting in when the power went.

## The cycle, which never stops

A processor does four things in a loop, a few billion times a second, from the
moment you switch the machine on until you switch it off.

::flow{numbered caption="The fetch–execute cycle. It has been running the whole time you have been reading this."}
  :::flow-step{label="Fetch" icon="i-lucide-download"}
  Read the instruction at the address the counter is pointing to.
  :::
  :::flow-step{label="Decode" icon="i-lucide-scan-line"}
  Work out which operation that pattern of bits means. Add? Compare? Jump?
  :::
  :::flow-step{label="Execute" icon="i-lucide-zap" highlight}
  Do it — using the gates from the last lesson.
  :::
  :::flow-step{label="Advance" icon="i-lucide-arrow-right"}
  Move the counter to the next instruction, and go round again.
  :::
::

An `if` statement is that counter jumping somewhere other than the next
instruction. A loop is it jumping backwards. A method call is it jumping away and
remembering where to come back to. Every control structure you will meet in the
Java track is a variation on changing that one number.

## Memory: numbered boxes

Main memory — RAM, for random-access memory — is one enormous row of numbered
boxes. Each box holds a byte. The number of the box is its **address**.

::memory{kind="array" caption="Four bytes of main memory during an admissions run. The address is the label; the byte is the contents."}
---
cells:
  - { value: 87, label: "0x7A10" }
  - { value: 74, label: "0x7A11" }
  - { value: 91, label: "0x7A12", state: "active" }
  - { value: 0, label: "0x7A13", state: "ghost" }
---
::

"Random access" means the machine can reach box 7A12 as quickly as box 0 —
straight there, no scanning. That is the whole property, and it is what makes RAM
different from everything below it.

::warning{icon="i-lucide-alert-triangle"}
**RAM forgets.** It holds its contents only while it has power. Pull the plug and
every value in it is gone in the time it takes the capacitors to drain. This is
not a flaw to be engineered around; it is how the technology works, and it is why
every application you have ever used has a save button.
::

## Storage: the filing cabinet

Storage — an SSD or a hard disk — keeps its contents with the power off. It is
enormously larger and enormously slower. Everything in computing is a negotiation
between those two facts.

| | Main memory (RAM) | Storage (SSD) |
| --- | --- | --- |
| Keeps data without power | No | Yes |
| Typical size | 8–32 GB | 256 GB – 2 TB |
| Time to fetch a value | ~100 nanoseconds | ~100 microseconds |
| Cost per gigabyte | High | Low |
| What lives there | The program running now, and its data | Files, the database, the operating system |

The row that matters is the third one, and the units hide it. Storage is roughly
**a thousand times** slower than memory. If reading from RAM took one second,
reading from an SSD would take about seventeen minutes, and from a spinning hard
disk, most of a day.

::real-life{title="The report that took forty seconds and then took one" source="A university reporting tool"}
An attendance report read twenty-three thousand rows from disk, one row at a
time, checking each one. Forty seconds, every time anyone opened the dashboard.
The fix was not a faster machine. It was reading the rows once into memory and
working there — and later, an index so the database did not have to touch most of
them at all. Same data, same processor, same everything: the only change was how
far the machine had to reach.
::

## Between them: cache

There is a third layer, tiny and very fast, sitting on the processor itself.
Cache holds the handful of things being used right now, because even RAM is slow
compared to the processor.

::flow{direction="vertical" numbered caption="Each step down is bigger, cheaper and dramatically slower."}
  :::flow-step{label="Registers" icon="i-lucide-microchip"}
  A few dozen values, inside the processor. Instant.
  :::
  :::flow-step{label="Cache" icon="i-lucide-layers"}
  A few megabytes. A handful of processor cycles away.
  :::
  :::flow-step{label="Main memory" icon="i-lucide-memory-stick" highlight}
  Gigabytes. Hundreds of cycles away. Forgets when the power goes.
  :::
  :::flow-step{label="Storage" icon="i-lucide-hard-drive"}
  Hundreds of gigabytes. Roughly a thousand times slower than memory. Remembers.
  :::
::

You will never manage cache by hand. It matters because it explains why the
answer to "make it faster" is so often "touch less data" rather than "buy a
better machine".

## What confuses people here

The word "memory" is used for both, constantly, by people who should know better.

::compare{caption="Two sentences, said in the same meeting, both using the word 'memory'."}
  :::compare-side{label="The server ran out of memory — RAM" verdict="neutral"}
  The program asked for more working space than existed and was killed. A restart
  clears it. Nothing was lost from disk.
  :::
  :::compare-side{label="The server ran out of memory — disk" verdict="neutral"}
  The storage filled up, so nothing more could be written — logs, uploads,
  database writes, all failing. A restart changes nothing at all.
  :::
::

When somebody says memory, ask which. The two failures look nothing alike and
have nothing in common except the word.

The second confusion is more personal: **unsaved work lives in RAM.** The
document you have been editing for two hours exists as a pattern of switches
holding their state only because the power is on. Saving is the act of copying it
somewhere that survives. Every "I lost everything" story is this sentence,
learned the expensive way.

## What you can do now

You can say what a processor does in four words, explain what an address is, and
answer the two questions that started this lesson: things are slow because
something is reaching too far for data, and things are lost because they were
only ever in memory.

You can also now say precisely why your Java programs, two tracks from here, will
forget every applicant you entered the moment they stop. It is not a limitation
of Java. It is this lesson.

## Your turn

No code. Answer these in a sentence each, out loud if you can.

1. Your machine has 16 GB of RAM and a 512 GB SSD. You open a 4 GB video file.
   Where is it, and where is the part you are watching?
2. A program has been running for an hour and has built up a list of 4,200
   applicants. The power cuts out. What survives?
3. Somebody says "add more RAM, it'll be faster". When are they right, and when
   are they wrong?

::accordion
---
items:
  - label: Solutions
    icon: i-lucide-key
    content: "1. The file lives on the SSD. Only the section being played is copied into RAM, a chunk at a time — which is why you can watch a file larger than your memory. 2. Nothing the program built survives, unless it wrote it to storage. Anything already saved to disk is untouched. 3. They are right when the machine is running out of working space and is being forced to shuffle data to disk to cope — that swapping is catastrophically slow. They are wrong when the program is slow because it is reaching for the wrong data, or far too much of it, which is most of the time. More RAM never makes a bad query good."

items:
  - label: Why does an application have a save button at all?
    icon: i-lucide-circle-help
    content: Because everything the program is working on lives in RAM, which holds its contents only while it has power. Saving copies that state to storage, which keeps it without power. Applications that appear to have no save button — a notes app, an online document — are saving constantly on your behalf; they have not escaped the distinction, they have hidden it.
  - label: "Interviewers ask this — what is the difference between memory and storage, and why does it matter to a program?"
    icon: i-lucide-briefcase
    content: Memory is volatile, small, and roughly a thousand times faster; storage is persistent, large and slow. A program does its work in memory and must deliberately write anything it wants to keep to storage. It matters for two everyday reasons: data loss, when state was only ever in memory, and performance, when a program keeps reaching to disk for values it could have held in memory. If you can name the rough speed gap, you have already answered the follow-up.
