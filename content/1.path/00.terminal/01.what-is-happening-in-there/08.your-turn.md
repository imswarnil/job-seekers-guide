Producing beats recognising, so here is the producing. Paper and a pen for most
of it. Attempt every one before opening a solution — the answer is worth about a
tenth as much if you read it first, and you will not be able to tell the
difference until it matters.

## Why this matters in a job

Because the difference between "I read about binary" and "I can convert 87 in my
head" shows up on a whiteboard, unprompted, in front of someone with a pen.

## 1. Conversions, cold

No calculator.

1. The pass mark is `40`. Write it in eight-bit binary.
2. A hostel block has `192` rooms. Binary and hex.
3. `11001000` is an applicant's score. What is it, in decimal?
4. The colour of the "rejected" badge is `#f04e2e`. What is the red component in
   decimal, and how do you know?

::accordion
---
items:
  - label: Solutions
    icon: i-lucide-key
    content: "1. 40 = 32 + 8 → 00101000. 2. 192 = 128 + 64 → 11000000, and hex C0. 3. 128 + 64 + 8 = 200. 4. F0 → 15 × 16 + 0 = 240. You know because a hex colour is three bytes — red, green, blue — two hex digits each, and the first pair is red."
---
::

## 2. The number almost everybody gets wrong

A student ID is currently stored in one byte, and the university has run out of
numbers. Somebody proposes adding **one more bit**.

How many more students does that allow? Answer before reading on. Then:

::runner{lang="javascript"}
```javascript
for (const bits of [8, 9, 10, 16]) {
  console.log(bits, 'bits →', (2 ** bits).toLocaleString(), 'possible values')
}
```
::

::accordion
---
items:
  - label: Why one bit is not one more student
    icon: i-lucide-key
    content: "One extra bit doubles the range: 256 becomes 512, not 257. Every position added is worth twice the one before it, so capacity grows by doubling rather than by counting. It is the same reason 16 bits gives 65,536 rather than twice 9 bits. This is the intuition behind everything from IP address exhaustion to why a 64-bit counter will genuinely never overflow in your lifetime — and the reason people are surprised by it is that human counting is linear and binary capacity is not."
---
::

## 3. The rule with the brackets missing

The bursar wants: **scholarship holders, or students whose family income is below
the threshold and who have no outstanding dues** — those students are exempt from
the late fee.

Somebody writes the condition as:

```text
scholarship OR income_below_threshold AND no_outstanding_dues
```

1. Which students does that actually exempt?
2. Write the version that matches what the bursar said.
3. Here are five students. Work out both answers by hand.

| Student | Scholarship | Income below threshold | Outstanding dues |
| --- | --- | --- | --- |
| Ananya | yes | no | yes |
| Imran | no | yes | no |
| Meera | no | yes | yes |
| Rohit | yes | yes | no |
| Sana | no | no | no |

::accordion
---
items:
  - label: Solutions
    icon: i-lucide-key
    content: "AND binds tighter, so the written condition means scholarship OR (income_below_threshold AND no_outstanding_dues). That exempts Ananya, Imran and Rohit — and Ananya has outstanding dues, which the bursar did not intend. The intended rule is (scholarship OR income_below_threshold) AND no_outstanding_dues, which exempts Imran, Rohit and Sana… and now Sana appears, who has neither scholarship nor low income. Which means the bursar's sentence was ambiguous in English, not just in code. That is the real lesson: the argument with the bursar is the work. Write both readings out, take them back, and ask. Every experienced developer has learned to do this and every beginner writes the first reading and ships it."
---
::

## 4. Find the wrong number

A dashboard reports average attendance of **93%** across the university. The
registrar knows several classes are barely half full. The query is not broken and
throws no error.

Give three plausible reasons the number is wrong. You have not learned SQL — this
is about reasoning, not syntax.

::accordion
---
items:
  - label: Three reasons, and the habit underneath them
    icon: i-lucide-key
    content: "One — it only averages rows where attendance was actually recorded, and the worst classes are the ones nobody bothers marking. Two — it averages the per-class percentages rather than the underlying students, so a class of six with perfect attendance counts as much as a class of two hundred. Three — it includes students who have left, whose records stopped while they were still attending. The habit: a number that looks good is not evidence. Ask what was excluded, ask what was averaged, and check the row count against something you already know."
---
::

## 5. Predict the output

Do not run it first. Write down what you think each line prints, then run it.

::runner{lang="javascript"}
```javascript
const seats = 60
const applicants = 4210

console.log(applicants / seats)
console.log(Math.trunc(applicants / seats))
console.log(applicants > 4000 && seats > 100)
console.log(applicants > 4000 || seats > 100)
console.log(!(applicants > 4000))
```
::

::accordion
---
items:
  - label: Answers
    icon: i-lucide-key
    content: "70.16666666666667, then 70, then false (only one side is true, and AND needs both), then true (OR needs one), then false. If you got the last three right without hesitating, the truth tables have landed. If you had to think about the fourth one, reread the table — it is four rows and it pays for itself for the next forty years."
---
::

## 6. Where does it live?

For each, say whether it is in RAM, on disk, or both — and what happens to it if
the power cuts out right now.

1. The photograph you took this morning.
2. The half-written email in a browser tab.
3. The database of 4,200 applicants that a program loaded at startup.
4. The program itself, while it is running.

::accordion
---
items:
  - label: Answers
    icon: i-lucide-key
    content: "1. Disk. Survives. 2. RAM — unless the mail client has saved a draft to disk or to a server, which most now do every few seconds, precisely because of this lesson. 3. Both: the authoritative copy is on disk, the working copy is in RAM. The RAM copy dies and any change not yet written dies with it. 4. Both: the file stays on disk, and the running process — its memory, its variables, its position in the instructions — is in RAM and gone."
---
::

## 7. Count what is running

Open your system's activity monitor or task manager one more time, and write down
three numbers: how many processes are running, how much RAM is in use, and how
much disk is free.

You will not use these numbers. The point is that a month from now, when
something is slow, you will know where to look and roughly what normal looked
like — and almost nobody who has been programming for a year can say what normal
looks like on their own machine.
