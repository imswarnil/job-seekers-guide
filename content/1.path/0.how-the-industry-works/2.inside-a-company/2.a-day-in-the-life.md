## Why this matters in a job

Because "what does a software engineer do all day?" is the question that stops
most people from starting, and no roadmap answers it. Here is a real Tuesday.

## 09:30 — You read, before you type

Open the ticket you are on. Reread the requirement. Check the channel for
anything that broke overnight. Nobody writes code in the first thirty minutes;
the ones who do are usually the ones who write the wrong thing.

## 10:00 — Standup

Fifteen minutes, standing or not. Three sentences from each person: what I
finished, what I am on, what is blocking me. It is not a status report to a
manager — it is the team finding out who needs help.

::warning{icon="i-lucide-alert-triangle"}
The most common junior mistake is saying "no blockers" while quietly stuck. Say
you are stuck. That is what the ritual is for.
::

## 10:15 — The actual work

You pull the latest code, make a branch, and change perhaps forty lines. Around
half your time goes on reading code you did not write, working out where the
change belongs. This ratio never changes, at any level of seniority.

```bash
git pull origin main
git checkout -b fix/admissions-seat-count
# … edit, run, edit, run …
git commit -m "Count seats per programme, not per campus"
git push -u origin fix/admissions-seat-count
```

## 12:30 — You open a pull request

A PR is a request that your change be merged, plus an explanation of why. A
teammate reads it and comments. They will find something. That is the system
working, not a judgement on you.

## 14:00 — You review someone else's

Reading other people's code is half of how you learn the codebase, and the
fastest way to become useful to a team you just joined.

## 15:00 — Product asks a question

"If a student applies to two programmes, does the seat count twice?" Nobody
decided this when the ticket was written. This conversation is the job.

## 16:00 — It ships

Your PR is approved and merged. A pipeline runs the tests, builds the app and
deploys it — to a staging environment first, then to production. You did not
copy any files anywhere. If you find yourself copying files to a server by hand,
something has gone wrong organisationally, not personally.

## 17:20 — Something breaks

An alert fires: errors on the admissions page. The team's response, in order:

::steps{level="3"}

### Stop the bleeding

Roll back to the previous version. Fixing forward under pressure is how a small
incident becomes a long one.

### Find out what happened

Read the logs. Find the first error, not the loudest one.

### Fix it properly, tomorrow

With a test that would have caught it.

### Write it down

A short, blameless note: what happened, why, what changes so it cannot recur.
Blameless is not politeness — a culture that punishes the individual gets fewer
reports and more outages.

::

## The shape of the week

| | |
| --- | --- |
| Writing new code | ~30% |
| Reading existing code | ~30% |
| Reviews, meetings, questions | ~25% |
| Debugging and incidents | ~15% |

If you were expecting eight hours a day of typing new features, this is the most
useful thing on this page.

## The interview question this answers

**"Walk me through how a change of yours gets from your machine to users."**

Branch, commit, pull request, review, merge, automated tests, staging, production
— with a rollback if it misbehaves. Say those words in that order and you sound
like somebody who has done it.
